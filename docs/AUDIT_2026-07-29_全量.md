## 1. 高严重度（High）

### N-01 路由：half-open 探测名额泄漏，配置错误渠道永久卡死 HalfOpen
- **定位**：`internal/backend/agent/model/router.go:109-118`（`adapterFor` 失败路径）
- **场景**：某渠道熔断后 Open→HalfOpen 放行探测（`permit.UsedHalfOpenPermit=true`）。若该渠道 Provider 配置类型不是 openai/anthropic（typo / 未支持类型），`adapterFor` 返回 `aerr`，路由 113-117 行直接 `continue`，既不调 `RecordSuccess` 也不调 `RecordFailure(permit.UsedHalfOpenPermit)`。`halfOpenInFlight` 卡在 1 永不释放；`AllowRequest()` 的 `allowHalfOpenProbeLocked` 见 `halfOpenInFlight>=1` 恒拒绝；`shouldRecoverLocked` 只在 Open 态检查超时，HalfOpen 不恢复 → 渠道永久不可用，只能人工 `Reset()`。
- **建议**：113 行 `continue` 前补 `cb.RecordFailure(permit.UsedHalfOpenPermit)`；或 `adapterFor` 之前的 `aerr` 分支显式 `releaseHalfOpenPermit`。补 `router_failover_test`：half-open 渠道 + 不支持 provider 类型 → 不应永久卡死。
- **关系**：新发现。属 B2 候选链 + A1 熔断器集成的边界泄漏，非 F-01/F-06/F-07/F-09/M2。

### N-02 路由：401/403/404 一律禁 failover，坏渠道直接阻塞用户而非切副渠道
- **定位**：`internal/backend/agent/model/router.go:160-165`
- **场景**：主渠道 API key 失效（401）或模型名拼错（404）。`sinkStarted=false`、`isClientSideCancellation=false` → `RecordFailure` 计数，但 `isRetryableChannelError` 判 401/403/404 不可重试 → 160-165 行 `return lastErr`。即使配置了正确的副渠道也永远不会被尝试。BYOK 场景下每个渠道有独立 API key/模型名，401/403/404 是 per-channel 问题，换渠道很可能成功。用户每次首请求都直接返回 401，除非连续重试 4 次触发熔断后才间接走副渠道。
- **建议**：放宽 F-07：401/403/404 应允许 failover（仍计 `RecordFailure` 让坏渠道最终熔断）。区分 401（鉴权，换渠道大概率成功）vs 400（请求体本身有问题，换渠道也失败）——400 仍禁 failover，401/403/404 放行。补测试：主渠道 401 → failover 到副渠道成功。
- **关系**：**F-07 ◑ 留后续**——给出明确建议：401/403/404 放宽（BYOK per-channel key 场景），仅 400 保守。

### N-03 Agent：Anthropic 无参工具 `input_schema:null` 触发 400，Anthropic 通道工具调用全挂
- **定位**：`internal/backend/agent/model/anthropic.go:265-269`（`InputSchema: descriptor.Function.Parameters` 透传 nil）
- **场景**：工具定义无 `parameters` 字段（部分 MCP 工具 / 纯枚举工具）时，`descriptor.Function.Parameters` 为 nil（map 零值）。`anthropicTool{InputSchema: nil}` 经 `json.Marshal` 得到 `"input_schema":null`。Anthropic Messages API 要求 `input_schema` 必须是对象（至少 `{}`），收到 `null` 返回 `400 invalid_request_error`。整个 agent turn 在首个 tool-calling 请求即失败，**所有 Anthropic 通道的工具调用不可用**。
- **建议**：`InputSchema` 为 nil 时填充 `map[string]any{"type":"object","properties":{}}`；或定义 `anthropicInputSchema` 类型实现 `MarshalJSON` 对 nil 输出 `{}`。加单测覆盖无参工具。
- **关系**：新发现。

### N-04 Agent：`AwaitShell` 退化为一次性快照，`block_until_ms` 从不阻塞，shell 等待语义失效
- **定位**：`internal/backend/forwarder/await_shell_tool.go:102-169`（`awaitShellSnapshot` 同步返回；`handleAwaitShellToolInvocation:57`、`completeImmediateToolResult:67,72`）
- **场景**：模型调用 `AwaitShell(shell_id, pattern, block_until_ms=30000)` 期望最多阻塞 30s 直到 pattern 匹配或 shell 结束。实际：`awaitShellSnapshot(102)` 内 `refreshBackgroundShellFromTerminalFile(116)` 读一次 terminal 文件，取当前 `StdoutBuffer[stdoutStart:](131)`，计算 `timedOut := blockUntilMS>0 && !matched && !isTerminal(157)` 立即返回（160-169）。`completeImmediateToolResult(72)` 马上回工具结果。模型拿到的几乎总是 `{matched:false, timed_out:true}` + 调用瞬间的部分输出，即便 shell 随后立即产出匹配行也看不到。agent 误判命令未完成、反复重跑或错误推进，**长任务/构建场景彻底失效**。
- **建议**：实现真正的阻塞等待循环——按 `block_until_ms` 设 deadline，周期性 refresh+读 buffer，匹配或 shell 终态即返回，超时返回 `timed_out`。或对齐 Cursor 的 `sinkStarted` 异步语义，把 AwaitShell 改为流式 tool result（先返回 pending，后续推送增量）。
- **关系**：新发现。

### N-10 生命周期：A6 写 Cursor `settings.json` 无 fsync/O_EXCL/Windows rename 重试，与 F-13 标准不一致
- **定位**：`internal/cursor/settings.go:301-309,373-379,443-449`（`RestoreCursorSettingsFromCrash` / `WriteUserProxySettings` / `ClearUserProxySettings`）
- **场景**：A6 Cursor `settings.json` 写入用固定名 `settingsPath+".tmp"` + 裸 `os.WriteFile(0o644)` + 一次性 `os.Rename`，无 fsync、无 O_EXCL、无 Windows rename 重试。与同仓库 F-13 级崩溃一致性标准（`forwarder.writeJSONFileAtomic`：唯一 tmp 名 + Sync + rename 重试 + 目录 sync）不一致。崩溃窗口一：`WriteFile` 写完 `.tmp` 但未 `Rename` 时进程被杀，留半截 `settings.json.tmp`（Cursor 目录下，0755 多用户可读）。崩溃窗口二：`Rename` 完成但数据仍在 OS page cache 未落盘——断电/系统崩溃时 `settings.json` 可能零字节或截断。Windows 上更严重：Cursor 编辑器进程持有 `settings.json` 句柄时 `os.Rename` 失败（`ERROR_SHARING_VIOLATION`），一次性 Rename 不重试 → `ClearCursorSettings` 在退出路径直接返回 error，用户原始代理配置未还原。

- **关系**：新发现（A6 引入）。F-13 已为 forwarder state/context 达成崩溃一致性，但 A6 对 Cursor settings.json 未对齐同一标准。

### N-11 生命周期：A6 备份"仅当无备份时写"存在 TOCTOU，`securefile.WriteFile` 非 O_EXCL
- **定位**：`internal/cursor/settings.go:132-162`（`writeCursorSettingsBackup`）+ `internal/securefile/securefile.go:36-44`（`WriteFile`）
- **场景**：`writeCursorSettingsBackup` 先 `os.Stat` 判定备份不存在，再 `securefile.WriteFile` 写入。但 `securefile.WriteFile` 用 `os.WriteFile`（`O_CREATE|O_WRONLY|O_TRUNC`，**无 O_EXCL**），非独占创建。`ShutdownForQuit` 用 `lifecycleMu.TryLock()` 非阻塞——拿不到锁（`StartProxy` 正在跑）就放弃等待直接走清理。此时若 `StartProxy` 的 `ApplyCursorSettings→WriteUserProxySettings` 正在 `writeCursorSettingsBackup`，而 `ShutdownForQuit` 的 `ClearCursorSettings` 或其他并发调用也走到 `writeCursorSettingsBackup`：两者都 Stat 看到"不存在"→ 都 WriteFile → 后写者覆盖先写者。更危险：cursor-switch 崩溃后重启，`StartProxy` 调 `RestoreCursorSettingsFromCrash`（会 `removeCursorSettingsBackup`），同时若另一路径进入 `writeCursorSettingsBackup`，可能在 restore 清掉备份后、又把当前已注入的污染值当原始值重新备份。
- **建议**：`securefile` 加 `WriteFileExclusive`（`os.OpenFile O_CREATE|O_EXCL|O_WRONLY`，已存在即返回 errExist，调用方据 Stat 判定是"自己之外有人写了"并放弃）。`writeCursorSettingsBackup` 改用独占创建，Stat 检查改为"尝试独占创建，失败说明已有备份或并发写者，保留不动"。
- **关系**：新发现（A6 引入）。H3 relayauth proof 的 `sync.Once` 单例竞态已修，但 A6 备份的"检查-then-写"是同类 TOCTOU。F-35 `lifecycleMu` 串行化覆盖正常 Start/Stop/Save，但 `ShutdownForQuit` 的 TryLock 主动放弃路径不在该保护内。

### N-12 计费：`turn_finalized` 事件 ModelID 恒空，被当 legacy 处理致误标异常 + input 成本漏算

### N-30 性能：runtime_summary 每 turn 边界 2 次 state.json 读改写
- **定位**：`internal/backend/forwarder/runtime_summary.go:107-176`（`syncConversationRecord` → `CreateConversation` + `UpdateConversationMeta`）

### N-31 性能：file_lock 争用时 10ms 轮询，延迟放大器
