> 审计日期:2026-07-29
> 审计范围:全量代码(Go 后端 + Vue3 前端 + cursor-tab-server + 构建配置),**未参考项目 `docs/` 目录下任何既有审计文档**,为独立审查结论。
> 审计方法:6 个并行子代理分领域深度审查 + 主审交叉验证关键 P0/P1,所有发现均附 `file:line` 与复现场景。

## 一、总体结论

cursor-byok 是一个工程化程度相当高、安全意识强的本地 Cursor MITM 代理。核心架构——**三条控制面分离**(身份/订阅/推理)、**多 provider 候选链 + 熔断 failover**、**每机器独立 CA + ed25519 更新签名**、**FRESH/TOTAL/legacy 三口径成本引擎**——设计扎实,代码注释详尽且可追溯。

但全量审查后发现若干**真实可触发的缺陷**,集中在四类:

| 类别 | 严重度 | 数量 | 典型代表 |
|---|---|---|---|
| 资源泄漏 / 内存耗尽 | P0 | 3 | AwaitShell 正则 goroutine 泄漏、后台 shell 无界 buffer、half-open permit 漏放 |
| 计费 / 状态正确性 | P1 | 6 | EventIndex prune 漏算 turn 计费、熔断错误率不滑动、RequestKnobs 共享 map 污染 |
| Cursor 能力缺失 | 结构性 | 4 | @codebase / @docs / Repository Index 全桩化、Tab 补全未 BYOK |
| UIUX / 可访问性 | P1-P3 | 多 | i18n 半成品、Config 路由模式不持久化、EChart 无 ResizeObserver |

**最该立即修的 5 条**(按影响 × 可触发性排序):
1. [P0] AwaitShell 正则 goroutine 泄漏 + ReDoS(`await_shell_tool.go:353-365`)
2. [P0] 后台 shell StdoutBuffer/StderrBuffer 无界增长 → OOM(`await_shell_tool.go:784,792`)
3. [P0] 熔断 half-open permit 在下游 sink 写失败时泄漏,渠道永久卡死(`router.go:142-161`)
4. [P1] `applyChannelToRequest` 原地修改共享 `RequestKnobs` map,failover 跨候选污染(`router.go:344-373`)
5. [P1] F-20 截断判定过激:不发 `[DONE]`/`message_stop` 的第三方中转正常完成被判截断,用户看到完整回复 + 报错(`openai.go:829`、`anthropic.go:751`)

## 二、P0 — 严重(数据损坏 / 资源耗尽 / 安全 / 崩溃)

### P0-1 AwaitShell 正则匹配超时后 goroutine 泄漏 + ReDoS CPU 占用 ✅ 已修复(上轮)
**位置**:`internal/backend/forwarder/await_shell_tool.go:337-366`

**问题**:`awaitShellPatternMatched` 启动一个 goroutine 跑 `expr.FindString(output)`(line 353-356),`select` 用 `time.After(2s)` 兜底(line 363)。超时分支直接 `return`,**未取消该 goroutine**。Go 的 `regexp.FindString` 不可中断,该 goroutine 在超时后继续回溯直到自行结束。

**复现场景**:模型调用 `AwaitShell` 且 pattern 是病态正则(如 `(a+)+$`),shell 输出含长串 `a`。2s 后函数返回 error,但泄漏的 goroutine 持续吃 CPU 回溯。每次 `AwaitShell` 调用(含 `awaitShellSnapshot` line 234 的二次调用)都新增一个不死的 goroutine,并发多 stream 累积,长跑进程逐步退化。pattern 已限长 512 字符,但回溯复杂度仍可达指数级。

**建议**:对 shell output 先做长度上限截断(见 P0-2)再匹配;或 pattern 编译时用 `syntax.Compile` 检测嵌套量词复杂度,过复杂直接拒绝;或对 output 长度设硬上限。

**✅ 修复**:Go 的 `regexp` 是 RE2(线性时间、无回溯),ReDoS 不适用——故放弃嵌套量词检测(会误杀合法 pattern)。改为对 `output` 按 `awaitShellPatternInputLimit=32KiB` 做尾部截断后再交给 goroutine 匹配,使泄漏 goroutine 在有界输入 + RE2 线性下必然有界结束。参见 `await_shell_tool.go` `awaitShellPatternMatched`。

### P0-2 后台 shell StdoutBuffer / StderrBuffer 无界增长 → 内存耗尽 ✅ 已修复(上轮)
**位置**:`internal/backend/forwarder/await_shell_tool.go:784,792,812,821`、`appendBackgroundShellBuffer:991-1000`

**问题**:`observeShellStreamLocked` 对 `state.StdoutBuffer += execbridge.DecodeShellStdout(...)`、`state.StderrBuffer += event.Stderr.GetData()` 做**无界字符串拼接**,无任何上限。`appendBackgroundShellBuffer` 同样无界。`awaitShellSnapshot` 只前移 `AwaitStdoutOffset`,buffer 本身从不裁剪。

**复现场景**:模型起一个后台 `Shell` 跑 `yes` 或 `find /` 之类持续刷屏命令,stream 存活期间每个 stdout chunk 都累加进 buffer。一个长跑 stream + 高频输出 → 该 stream 的 `BackgroundShells` map 内单个 state 占内存线性增长,多 stream 叠加可 OOM。`truncateAwaitShellOutput`(line 368)只裁剪返回给模型的快照切片,不裁底层 buffer。

**建议**:给 `BackgroundShellState.StdoutBuffer/StderrBuffer` 设容量上限(如 1MiB),超限保留尾部(环形或 `buffer = buffer[len-1MiB:]`),与 `awaitShellOutputLimit` 复用常量。

**✅ 修复**:引入 `awaitShellBufferCap=256KiB` 与 `appendShellStreamBuffer`/`clampShellBuffer` 有界 helper,所有 `StdoutBuffer +=`/`StderrBuffer +=`(await_shell_tool.go 与 tool_invocation.go)改走 helper,超限保留尾部。`awaitShellSnapshot` 返回切片也经 `clampShellBuffer`。

### P0-3 熔断 half-open 探测名额在"下游 sink 写失败"路径泄漏,渠道永久卡死 HalfOpen ✅ 已修复(上轮)
**位置**:`internal/backend/agent/model/router.go:142-161` + `circuit_breaker.go:197-220`

**问题**:`RecordSuccess`/`RecordFailure` 是释放 half-open permit 的**唯一路径**(`circuit_breaker.go:197-199, 218-220`)。router.go line 142 成功路径(`streamErr==nil && sinkErr==nil`)调 `RecordSuccess`;line 157 失败路径条件是 `!isClientSideCancellation && sinkErr == nil` 才调 `RecordFailure`。当 **`streamErr==nil` 但 `sinkErr!=nil`**(provider 正常完成流,但下游 sink 写入报错,如客户端连接断开但 ctx 尚未取消)时,**两个分支都不命中**,`permit.UsedHalfOpenPermit==true` 时 `halfOpenInFlight` 永不递减。

**复现场景**:渠道处于 HalfOpen,放行 1 个探测请求。provider 正常返回完整流,`adapter.Stream` 返回 `nil`;但 sink 包装器在写中途某事件时返回错误(forwarder 管道已关闭但 ctx.Err() 仍为 nil,取消尚未传播)。`effErr=sinkErr` 非空、`sinkErr!=nil` → 跳过 RecordFailure;`streamErr==nil` → 跳过 RecordSuccess。`halfOpenInFlight` 卡在 1,该渠道永远无法再放行探测请求,只能人工 Reset。逐个渠道累积后,所有候选最终全部卡死 HalfOpen。

**建议**:把"释放 half-open permit"从 RecordSuccess/RecordFailure 的语义里拆出,在 router 末尾用 `defer` 保证一定释放一次;或在 `effErr!=nil && sinkErr!=nil` 分支也调用一次释放(仅释放名额,不污染统计)。

**✅ 修复**:`*CircuitBreaker` 新增 `ReleaseHalfOpenPermit(usedHalfOpenPermit bool)`(仅释放名额、不更新统计),在 `router.go` 的 `streamErr==nil && sinkErr!=nil`(client cancel / sink 写失败)等非 provider 失败路径显式调用。回归测试 `router_halfopen_permit_sink_test.go`。

### P0-4 state.vscdb 与正在运行的 Cursor 进程并发写竞争,可损坏用户状态库 ✅ 已修复(上轮)
**位置**:`internal/cursor/state_db.go:76-131,247-319` + `internal/client/lifecycle.go:152`

**问题**:`StartProxy` 调 `cursor.RepairLegacyInjectedIdentity()`,后者 `sql.Open("sqlite", stateDBPath)` 并 `BeginTx` 写。该文件是 **Cursor 进程正在使用的同一 `state.vscdb`**。虽有 `SetMaxOpenConns(1)` + `PRAGMA busy_timeout=2000`,但 SQLite WAL 模式下一个写事务阻塞其他写者;若 Cursor 正在写,byok 的 `BeginTx` 等 2 秒后失败,假账号残留不被清理(StartProxy 不回滚,仅记日志)。更严重:若 Cursor 升级后改了 ItemTable schema,byok 的 `CREATE TABLE IF NOT EXISTS` 与 Cursor schema 冲突,或 BLOB 编码不符,导致 Cursor 读取崩溃或状态丢失。

**复现场景**:用户启动 byok 时 Cursor 正在运行并持有 state.vscdb 写锁,byok 的修复等待 2 秒后 `SQLITE_BUSY` 失败;或 Cursor 与 byok 交错写导致 statsig bootstrap JSON 损坏,UI 异常。

**建议**:`RepairLegacyInjectedIdentity` 改为**只在 Cursor 进程未运行时执行**(检测 Cursor 进程);彻底移除 `InjectCursorUserInfo` 死代码(见 P3-1)。

**✅ 修复**:`RepairLegacyInjectedIdentity` 入口加 `isCursorProcessRunning()` 检测(`process_running_unix.go` pgrep / `process_running_windows.go` tasklist),Cursor 运行时跳过修复。`InjectCursorUserInfo` 及其辅助函数(`buildCursorAuthStateValues`/`syncCursorAuthStateDB`/`disableCursorStatsigGate`/`cursorStateDJB2Hash`)作为 P3-1 死代码一并移除,对应测试同步删除。另增只读 `ProbeCursorAccount` 用于前端"Tab 依赖官方账号"告警(不写库)。

### P0-5(已驳回)自动更新 manifest 签名 map 序列化不可靠 — **误报,已实证否定**
子代理原报告称 `canonicalManifestBytes` 用 `json.Marshal` 处理含 `map[string]manifestPlatform` 的结构,map 迭代顺序随机化会导致验签不可靠。**经主审实证验证**:Go 标准库 `encoding/json` 对 map **按键排序**(文档保证行为),同一 struct 在任意进程 `json.Marshal` 产出的字节序列是确定性的。签名方(`scripts/release/main.go:335`)与验证方(`updater/pubkey.go:58`)均用 `json.Marshal`,且 release 脚本注释明确"matches updater.canonicalManifestBytes"。**签名机制健全,此条不成立。**

但相关真实风险见 P1-1(payload exe 无代码签名)。

## 三、P1 — 高(功能 bug / 计费 / 并发 / 能力偏离)

### P1-1 自动更新安装链对 payload exe 不做代码签名校验
**位置**:`internal/updater/manager.go:412,715,744-751`

**问题**:`spawnWindowsInstaller` 用 `powershell -ExecutionPolicy Bypass` 执行,`windowsInstallerScript` 对 `Expand-Archive` 内容用 `Copy-Item -Force` 覆盖目标目录后 `Start-Process` 直接启动。整个安装链**只依赖 manifest ed25519 签名 + SHA256 checksum 闭环**(二者均来自已验签 manifest),但对解压出的**可执行文件本身不做 Authenticode/macOS notarization 校验**。checksum 闭环本身健全(P0-5 已驳),但纵深防御薄。

**复现场景**:若未来公钥泄露或签名密钥被攻破,任意代码经签名 manifest 即可执行;或下载链路被中间人重定向(`Manager.client` 跟随 3xx,无 host 白名单)到非预期源,只要攻击者持有签名密钥即可。

**建议**:下载强制 HTTPS + 目标 host 白名单(GitHub 域族);安装前对解压 exe 做 Authenticode/notarization 校验;引入公钥轮换机制(多公钥 + keyId)。

### P1-2 F-20 截断判定过激:无 `[DONE]`/`message_stop` 的正常完成被判截断,已发文本丢失 ✅ 已修复(上轮)
**位置**:`internal/backend/agent/model/openai.go:829-831,680-692` + `anthropic.go:751-755`

**问题**:`sawTerminator` 只在收到 `[DONE]`(OpenAI)或 `message_stop`(Anthropic)或 `finish_reason!=nil` 时置真。部分第三方中转在流末尾直接 EOF 不发终止符,且最后一 chunk 不带 finish_reason。此时 `sawTerminator==false` → 返回 `streamTerminatorMissingError` → Router 因 `sinkStarted==true`(文本已发)不 failover,直接透传错误。用户看到完整回复后紧跟"stream truncated"错误。

**复现场景**:用户配置两个第三方 OpenAI 兼容渠道均不发 `[DONE]`,流式文本正常输出完毕后 EOF,用户得到完整回复 + 截断报错。

**建议**:F-20 防的是"零事件空成功",应增加"已发过有效 content/tool 事件则 EOF 视为成功"的降级(加 `emittedAny bool` 闸门),仅在零事件 200 时才视作截断。

**✅ 修复**:OpenAI(Chat Completions/Responses 两路)与 Anthropic 适配器均加 `emittedAny bool` 闸门,emitTextDelta/emitThinkingDelta/工具事件处置真;截断判定改为 `if !sawTerminator && !emittedAny`(Responses 路 `!sawTerminator && !emittedText && !emittedToolInvocation`)。已发有效事件的 EOF 不再判截断。

### P1-3 `applyChannelToRequest` 原地修改共享 `RequestKnobs` map,跨候选污染 ✅ 已修复(上轮)
**位置**:`internal/backend/agent/model/router.go:344-373` + `thinking_rectifier.go:44-92`

**问题**:`resolved := req`(line 298)是值拷贝结构体,但 `resolved.RequestKnobs`(map)是**引用拷贝**——与 `req.RequestKnobs` 指向同一 map。line 344-373 直接对 `resolved.RequestKnobs` 做 `delete`/写入。每次 failover 对每个候选调一次 `applyChannelToRequest`,后一候选的 knob 覆盖/残留前一候选的(如 `openai_endpoint` 在切到 anthropic 候选时未被清除)。`thinking_rectifier` 的 `setThinkingRectified` 也写共享 map,导致 `thinking_rectified=true` 跨候选泄漏,违反"每候选整流一次"设计意图——下一候选首试失败后不再整流。

**复现场景**:候选链 [openai-channel-A, anthropic-channel-B]。对 A 写 `RequestKnobs["openai_endpoint"]=...`,A 失败 failover 到 B,对 B 走 anthropic 分支,`openai_endpoint` 仍在 map,artifact 记录的 B 请求带无关 knob;若 A 整流重试仍失败,`thinking_rectified` 泄漏到 B,B 不再整流。

**建议**:`applyChannelToRequest` 内对 `RequestKnobs` 做深拷贝:`resolved.RequestKnobs = copyMap(req.RequestKnobs)`;`setThinkingRectified` 应写 per-channel map 或在 `applyChannelToRequest` 清除 `thinking_rectified` knob。

**✅ 修复**:`applyChannelToRequest` 入口对 `req.RequestKnobs` map 做深拷贝,per-candidate knob 写入不再污染跨 failover 的原 map。

### P1-4 熔断错误率算法不滑动,健康渠道被反复熔断 ✅ 已修复(上轮)
**位置**:`internal/backend/agent/model/circuit_breaker.go:200-239`

**问题**:`RecordSuccess` 只清 `consecutiveFailures`(line 200),**不清** `failedRequests`/`totalRequests`(继续累计)。Closed 状态下错误率 = `failedRequests/totalRequests` 用全期累计(line 233-235)。渠道经历 9 失 1 成后又 1 失:`consecutiveFailures=1`(未达 4),`totalRequests=11`,`failedRequests=10`,错误率 10/11≈0.91 ≥ 0.6 → **Open**。一次成功后紧接着单次失败即熔断。

**复现场景**:渠道偶发抖动,历史 10 次请求 9 失 1 成,随后恢复 1 次成功,再 1 次失败——错误率把"一次成功"计入分母但不清分子,错误率长期偏高,健康渠道反复熔断。

**建议**:`RecordSuccess` 在 Closed 状态下衰减 `failedRequests`,或错误率改用滑动窗口(环形缓冲最近 N 次)而非全期累计。

**✅ 修复**:`CircuitBreaker` 加 `recentResults []bool`(窗口 50)+ `windowFailed`,新增 `recentErrorRateLocked()` 用滑动窗口而非全期累计判熔断;`transitionToClosedLocked` 重置窗口。全期统计仍累积用于可观测。回归测试 `circuit_breaker_sliding_test.go`。

### P1-5 EventIndex 达 5000 上限后裁剪,旧 provider_call 事件丢失 → turn 计费漏算 ✅ 已修复(上轮)
**位置**:`internal/backend/forwarder/usage_store.go:429-449` + `token_usage.go:386-407`

**问题**:`pruneUsageEventIndex` 在 `len(index) > 5000` 时按 `At` 降序保留最近 5000 条,淘汰最老。`recordTurnFinalizedSnapshot` 走 `UpsertTurnFinalized`,内部 `lookupUsageEventInDoc` 聚合该 requestID 的所有 provider_call 子事件。若该 turn 的某些 provider_call 子事件(failover 链下可能有多个 modelCallID 子事件)已被 prune 淘汰,聚合到的 token 数偏小,turn 事件 Input/Output/Cache 被写成偏小值,**永久落盘**,dashboard 按模型计成本偏低。

**复现场景**:高活跃单进程,累计 distinct EventID 超过 5000。早期某 turn 的 provider_call 事件被淘汰,该 turn 的 turn_finalized 后到(异步 finalize + 进程重启后触发)→ 聚合到 0,计费丢失。

**建议**:`turn_finalized` 事件不参与 prune(或其保留优先级高于 provider_call);或 prune 时只淘汰其 requestID 已有对应 turn_finalized 落盘的 provider_call 条目。

**✅ 修复**:`pruneUsageEventIndex` 改为只淘汰"已有对应 `turn_finalized` 落盘"的 `provider_call` 条目;`turn_finalized` 事件免 prune。另 N-38 把 EventID 分隔符改 `\x1f`,消除 requestID 含 `::` 时串账。

### P1-6 `appendSequenceTracker.Release` 在异常路径漏调则永久死锁
**位置**:`internal/backend/forwarder/append_seq.go:106-133`

**问题**:`Release` 只在 `state.processing && state.next == seq` 时推进 `next++` 并 close ready。若调用方持票后因 error 提前 return 但未调 Release,或传错 seq,`state.processing` 保持 true、`next` 不前进,后续所有 `Acquire` 阻塞在 `<-ready`(ctx.Done() 是唯一出口)。`expired`(line 129)在 `processing==true` 时返回 false → 永不回收,该 requestID 的 append 序列永久死锁。

**复现场景**:`BidiAppend` 处理某 appendSeq 时 panic/error 路径未 `ticket.Release()`,该 stream 后续所有 append 顺序消息永久阻塞,客户端看到流卡死。

**建议**:`Release` 放宽为只要 `state.processing && seq >= state.next` 就推进(容错乱序释放);给 tracker 加 watchdog timer,processing 超过 `appendSequenceRetention`(10min)强制 reset;审计所有 `Acquire` 调用点确保 `defer ticket.Release()`。

### P1-8 乐观更新回滚与磁盘真值脱节 ✅ 已修复(上轮)
**位置**:`frontend/src/state/appState.js:1258-1261,1279-1282` + `watchSyncEffect:969-1001`

**问题**:`savePerNamespaceRoute`/`saveTabServerBaseURL` 先改 `appState`(乐观更新),再 `persistConfigPayload`(内部 `saveUserConfig` + `loadPersistedUserConfig` + `applyConfigToState`)。若 `saveUserConfig` 成功但回读/`applyConfigToState` 抛错(网络抖动、Wails 超时),`finally` 只置 `configSaving=false`,异常冒泡触发 `appState = previous` 回滚——**此时磁盘已是新值,但 appState 回滚到旧值**,UI 显示与磁盘不一致;且 `watchSyncEffect` 会把回滚后的旧值写回 localStorage 缓存,固化错位。

## 七、安全审查专项结论(无 P0 安全漏洞)

三条控制面分流的安全核心**设计扎实**:

- **凭证目标绑定 + fail-closed 恢复**:`CaptureAndStripCredentials`(`context.go:95`)只对 MITM 来源捕获并绑定 `BoundTarget`;`restoreOriginalCursorCredentials`(`client.go:130`)恢复前强制 HTTPS + `isCursorHost` + 标准端口 + `BoundTarget` 一致性校验。
- **NoRedirect 强制**:`CredentialOriginalCursor` 策略下无条件走 `NewHTTPClientNoRedirect`,provider 3xx 不会带凭证外泄。
- **SSRF 防护**:`safehttp` 抓取链完整(私网/loopback/元数据/DNS rebinding 全拒)。
- **路径逃逸**:`conversation` 目录 `validateConversationID` Clean + Rel 二次校验;workspace 写路径 `resolveWorkspacePathWithinRootReal` 双 `EvalSymlinks` 围栏,堵住 symlink 旁路。
- **文件安全**:`securefile` 原子写(`WriteViaTempSync`)+ Windows rename 重试 + 0600/0700 权限。
- **更新签名**:ed25519 验签前置(P0-5 已驳误报),签名+checksum 闭环健全。

**真实安全风险**仅有 P1-1(更新 payload exe 无代码签名,纵深防御薄)与 P2-9(@docs prompt injection)。无凭证泄露给第三方 provider 的路径。
