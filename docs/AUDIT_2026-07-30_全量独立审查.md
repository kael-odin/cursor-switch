# cursor-byok 全量独立审计报告

> 审计日期：2026-07-30
> 审计范围：全量源码（Go 后端 181 文件 / ~58k LOC + Vue3 前端 ~8.3k LOC），**未参考项目自带 docs/ 与既有审计结论**，纯独立审查
> 审计方法：5 路并行子系统审查（forwarder 数据面 / agent model 路由 / 安全面 / 控制面 / 前端 UIUX）+ 关键 P0 项人工复核验证
> 严重度分级：**P0** = 数据损坏/崩溃/资损/安全漏洞；**P1** = 重要功能错误或核心能力缺失；**P2** = 次要功能/体验/边界缺陷；**P3** = 优化建议

## 一、总体结论

项目整体工程化水平与安全基线**显著高于一般 fork**：已闭合大量历史审计点（F-13 崩溃一致性、F-28 backlog 上限、F-30 图片数量/总量上限、F-32 workspace realpath 围栏、F-19 参数黑名单、ed25519 更新验签、每机独立 CA、relay proof 进程级认证、SSRF 防护 + DNS rebinding 固定 IP）。CI 跑 `go vet` + `go test` + `go test -race` + 前端 production build，覆盖度合理。

但本次审查仍发现 **P0×6 / P1×23 / P2×45 / P3×42 ≈ 116 项** 问题（去重后）。核心矛盾集中在四个方向：

1. **图生图端到端从未跑通**——入站阶段就裸字节截断二进制图片，破坏 PNG/JPEG 完整性，与既有诊断一致，根因在「超限截断」而非「超限丢弃」。
2. **成本估算系统性失真**——模型解析失败回退字面量 `default` 致跨适配器混算；per-adapter 倍率键维度错配；by_model 聚合键语义存疑。
3. **原 Cursor 核心能力缺失/降级**——@codebase 仅存路径元数据无任何检索召回；@docs 整篇单 chunk 返回无相关性排序；RepositoryService 全 stub；压缩丢弃 tool_result 原文/图片/reasoning signature。
4. **agent 主循环阻塞与并发竞态**——driveProvider/AwaitShell/cancelOtherConversationActors 在 actor 单线程上同步阻塞重 IO，致取消/中断延迟；多处裸读 stream 字段与 actor 写竞争。

> 说明：部分 finding 来自子代理报告，P0 与关键 P1 已由我人工复核 file:line（标记 ✅已验证）。其余为子代理结论，已交叉比对但未逐行复验，建议落地修复前按 file:line 再确认一次。

## 二、P0 严重问题（6 项，须优先修复）

### P0-1 ✅ 图生图参考图按字节硬截断，破坏 PNG/JPEG 二进制完整性
- **位置**：[interaction_tools.go:585-593](internal/backend/forwarder/interaction_tools.go)，[prompt_guard.go:149-157](internal/backend/forwarder/prompt_guard.go)
- **现象**：对 inline 图片二进制数据做 `data = data[:promptGuardSelectedImageMaxBytes]` 与 `data = data[:remaining]`，直接在二进制字节中间切片。PNG/JPEG 是结构化二进制，任意字节偏移截断产生损坏图像（截断的 IDAT/扫描数据），随后作为 multipart image part 发给 OpenAI `/v1/images/edits`，上游解码失败返回 400。
- **影响**：这正是「图生图从未真正端到端跑通」的核心根因之一。F-30 的字节上限本意是防外发过大文件，但用「裸切片」而非「超限丢弃整张」实现，把可用图也变成坏图。4MB 单图上限几乎必触发（截图/照片 base64 后 inline data 常 >4MB）。
- **修复建议**：超限应**整张丢弃并 log warn**（continue 跳过该图），而非截断字节；丢弃后给模型明确反馈「参考图 N 因过大被跳过」。若必须限流，应对 base64 解码后的原图做缩放/重编码而非裸字节切片。

### P0-2 ✅ 模型解析失败回退字面量 `default`，致 by_model["default"] 跨适配器混算成本
- **位置**：[service.go:415-416](internal/backend/forwarder/service.go)，[service.go:480-481](internal/backend/forwarder/service.go)，token_usage.go:328/354，usage_store.go applyUsageModelDelta
- **现象**：`extractRequestedModelID(message)` 解析失败时 `intent.ModelID` 硬编码为 `"default"`。该值经 OpenStream → stream.ModelID → provider_call 事件 ModelID → usage.json `by_model` 聚合键。所有解析失败的 turn 堆进 `by_model["default"]` 一个桶，不同 provider/适配器/真实模型的 token 与成本被混在一起。
- **影响**：定价按 `"default"` 查表必然 miss → 零价；per-adapter CostMultiplier 按 `"default"` 查 adapterMultipliers 也 miss → 回落全局倍率。这部分 turn 的成本估算系统性失真（归零或用错倍率），资损级。
- **修复建议**：解析失败时记录请求体原始模型字符串或标记 `unknown:<provider>`，而非笼统 `default`；或 recordTurnUsageSnapshot 时若 modelID==`default` 改用 provider 返回的 `usage.Model` 作 by_model 键。在 `by_model["default"]` 桶对成本引擎返回「无法估算」标记，避免给用户呈现错误零成本。

### P0-3 debug JSONL 明文记录完整请求体/工具参数/上下文，API key 与敏感数据泄露
- **位置**：[debug_recorder.go:49-87, 296-312](internal/backend/forwarder/debug_recorder.go)，artifacts.go:72
- **现象**：`LogBidiRaw` 写原始 `data_hex`（完整客户端请求体）到 `bidi.raw.jsonl`；`LogBidiDecoded` 经 protoJSONDebugPayload 全量序列化 AgentClientMessage（含 user message、conversation state、工具参数：文件内容/shell 命令/MCP 参数）；`provider.jsonl` 记录 session.requestPayload 可能含第三方 provider 的 Authorization 头或 API key。仅靠文件权限 0600/0700 保护，**无字段脱敏、无过期清理、无容量上限**。
- **影响**：本地 MITM 代理最敏感的落盘点；historyRoot 若被同步网盘（OneDrive/Dropbox）上传，则密钥/源码/凭据外泄。
- **修复建议**：对 data_hex/message/payload 做敏感字段递归脱敏（Authorization/api_key/token/password/secret → `***`）；为 debug 目录增加容量/时间上限的滚动清理；文档化 historyRoot 不应放网盘同步目录。

### P0-4 压缩摘要 goroutine 无锁读取 stream.RequestID/ConversationID/ModelID，与 actor 线程数据竞争
- **位置**：[compaction.go](internal/backend/forwarder/compaction.go) generateCompactionSummary ~L1446-1457，runPendingCompaction ~L386-414
- **现象**：runPendingCompaction 在独立 goroutine 调 generateCompactionSummary，后者直接读 `stream.RequestID/ConversationID/ModelID` 且未持 `stream.mu`。这些字段在 actor 线程可被并发修改（新一轮 provider pass 改写 CurrentModelCallID、OpenStream 刷新 ConversationID）。
- **影响**：`go test -race` 会报；运行期可能读到半更新值，导致摘要请求打到错误模型或带错误 request_id，usage 记录错位。
- **修复建议**：在 startPendingCompactionSummary 持锁段内把所需字段快照到局部变量/plan，goroutine 只读快照。

### P0-5 budget≤0 时跳过预算校验，压缩后仍超窗口的对话被放行致 provider context_length_exceeded
- **位置**：[compaction.go](internal/backend/forwarder/compaction.go) validateCompactionCandidateBudget ~L732-757
- **现象**：当 `ReserveTokens >= ContextWindowSize` 时 `budgetTokens <= 0`，函数直接 `return nil` 放行（`if budgetTokens > 0 && estimatedTokens <= budgetTokens`）。小窗口模型（ContextWindowSize≤16384，compactionReserveTokensFor clamp 下限 16384）触发。
- **影响**：即使压缩后 estimatedTokens 仍超窗口也不报 overflow，把超窗口 compiled 直接交给 provider，用户看到上游 `context_length_exceeded` 而非受控 overflow 终止。
- **修复建议**：budget≤0 时视为必然超限返回 compactionTerminalError；或至少 `estimatedTokens > plan.ContextWindowSize` 时直接报 overflow。

### P0-6 debug 日志文件无大小上限/无轮转，长对话下单个 jsonl 无限增长直至磁盘满
- **位置**：[debug_recorder.go:146-171](internal/backend/forwarder/debug_recorder.go)
- **现象**：appendJSONL 以 O_APPEND 持续追加，**无大小检查、无轮转、无截断**。五类 jsonl 文件随对话长度无限增长，一次超长流式对话可轻易产生数百 MB 单文件。配合 P0-3 的全量明文，磁盘耗尽风险真实存在。
- **影响**：historyRoot 所在盘写满，影响整个应用。
- **修复建议**：每类 jsonl 增加大小上限（如 10MB）+ 轮转（保留 N 份）；或全局 debug 磁盘配额，超限自动关闭 debug 并告警。

## 三、P1 重要问题（23 项）

### 业务逻辑 bug

#### P1-1 ✅ by_model 聚合键用 stream.ModelID 而非真实模型名，成本引擎按 model_id 定价算错
- **位置**：[token_usage.go:322-356](internal/backend/forwarder/token_usage.go)，usage_store.go:601
- **现象**：recordTurnUsageSnapshot 把 `stream.ModelID` 直接作 usageFileEvent.ModelID 写入；usage_store.go applyUsageModelDelta 以 `strings.ToLower(modelID)` 作 by_model 聚合 key。若 stream.ModelID 是渠道哈希/channel.ID，定价按 model_id 匹配会对不上真实模型。ModelName 虽写入但仅作展示，从不参与定价 key 路由。
- **注**：与 CTL-05 发现的「注释过时」并存——实际 by_model 键当前是请求侧模型名或 `default`，非通道哈希。但「优先用 ModelName 路由定价」的加固仍必要。
- **修复建议**：定价查找优先用 ModelName 匹配，ModelID 仅 fallback；或在写入 by_model 前用 resolver 还原真实 serverModelName 作聚合键。

#### P1-2 ✅ per-adapter CostMultiplier 键维度不一致，倍率静默失效
- **位置**：[metrics.go:315, 369](internal/bridge/metrics.go)，dashboard.go:249/342/402
- **现象**：loadAdapterMultipliers 按 `adapter.ModelID`（用户配的逻辑 ID）建倍率表，computeCostByModel 查表用 `usage.ModelID`（请求侧模型名或 `default`）。两者维度不一致，用户设的 per-adapter 倍率被静默忽略，回落全局倍率。
- **修复建议**：倍率匹配与定价匹配同策略（候选链归一化），或优先按 modelName 再按 modelId 查；对 `default` 桶显式标注无法应用 per-adapter 倍率。

#### P1-3 updateConversationTokenState 把 cacheWrite 计入 UsedTokens，高估上下文占用致过早压缩
- **位置**：[token_usage.go:239-267](internal/backend/forwarder/token_usage.go)
- **现象**：`promptTokensTotal = input + cacheRead + cacheWrite`，若 >0 覆盖 `UsedTokens`。但 cacheWrite（cache_creation_input_tokens）是本次写入缓存产生，**非已占用上下文**，计入会高估占用，过早触发 autoCompaction。
- **修复建议**：UsedTokens 只计 input + cacheRead，排除 cacheWrite；或直接用 provider 返回的 used_tokens 字段。

#### P1-4 legacy usage.json 迁移从已 trim 的 RecentEvents(500) 重建 EventIndex，老事件永久丢失
- **位置**：[usage_store.go:292-373](internal/backend/forwarder/usage_store.go)
- **现象**：readUsageFileDocument 对 legacy 文件在内存重建 EventIndex，但 RecentEvents 已被 trim 到 500 条，超过的老 provider_call 已丢失，重建索引只覆盖 500 条——老 turn 计费 finalize 时漏算。且只在下次写时落盘，只读 dashboard 不产生新 turn 则永不持久化。
- **修复建议**：legacy 迁移从磁盘原始未 trim 的 RecentEvents 重建；提供一次性迁移命令升级到完整 EventIndex。

#### P1-5 rewind 后未刷新 CurrentPlan/CurrentTodos，结构化状态停留旧 turn
- **位置**：[rewind.go:232](internal/backend/forwarder/rewind.go)，service.go:538-545
- **现象**：applyRunRewindConversationState 只重置 TokenDetails/loop/LatestRequestPrefix/LastProviderCall，**未重置 CurrentPlanText/CurrentPlans/CurrentTodos**。rewind 丢弃 targetTurnSeq 及之后条目，但派生字段仍指向被丢弃 turn 的结果。内存与 store 两路径都不调 refreshConversationRuntimeState。
- **影响**：用户回退到某轮后，注入 prompt 的 `<current_plan>`/`<todo_list>` 仍是回退前状态，模型基于过时计划工作。
- **修复建议**：rewind 落库与内存两条路径末尾都调 refreshConversationRuntimeState。

#### P1-6 handleCancelIntent 裸读 stream 字段与 OpenStream 并发写 data race
- **位置**：[service.go:653-695](internal/backend/forwarder/service.go) handleCancelIntent
- **现象**：直接读 `stream.ConversationID/TurnSeq/RequestID` 未持 `stream.mu`，而 OpenStream 在 existing.mu.Lock 下写这些字段。read/write race，race detector 会报。
- **修复建议**：handleCancelIntent 入口在 stream.mu.Lock 下一次性快照到局部变量。

#### P1-7 driveProvider 在 actor goroutine 上同步阻塞重 IO，cancel/中断延迟
- **位置**：[service.go:792-929](internal/backend/forwarder/service.go) driveProvider
- **现象**：driveProvider 跑在 stream actor 上，顺序执行 snapshotCheckpointConversation（克隆全量会话）、syncConversationContextWindowTokens、persistDerivedPromptContexts（落盘）、compiler.Compile（全量投影）、maybeCompactBeforeProvider、syncSummarySnapshot，然后才 `go runProviderStream`。长会话耗时数百 ms~秒级，期间 mailbox 不被消费：用户发 cancel 排在 mailbox 后面，agent 仍在跑、UI 无响应。
- **修复建议**：编译/落盘/压缩判定移出 actor 到独立 worker goroutine，完成后 postStreamCommandAsync 回投；cancel 命令始终能被 actor 及时消费。

#### P1-8 cancelOtherConversationActors 在当前 actor 内同步等待兄弟流，阻塞并跨 actor 串行化
- **位置**：[service.go:513-519](internal/backend/forwarder/service.go)，actor.go:1061-1081
- **现象**：handleRunIntent 在 stream A 的 actor 上对每个兄弟流 B 调 postStreamCommandWait（阻塞等到 B 收口）。A 的 actor 被挂起，期间 A 无法处理任何命令；单次 run 延迟被兄弟流 cancel 处理时间线性叠加。
- **修复建议**：改用 postStreamCommandAsync 非阻塞投递，不在当前 actor 等待兄弟流。

#### P1-9 ProviderCancel 在 driveProvider 与 broker.Cancel 间存在窗口，cancel 后仍可能发上游请求（计费/资损）
- **位置**：[service.go:887-893](internal/backend/forwarder/service.go)，broker.go:451-454
- **现象**：driveProvider L797 检查 status 在 L830 解锁；L889-893 重新加锁置 ProviderActive=true/ProviderCancel=cancel。两段锁之间 status 可被 broker.Cancel 改写，driveProvider 仍会 go runProviderStream，新 goroutine 跑起来才发现 status=Canceled，但期间已发上游 LLM 请求。
- **修复建议**：driveProvider L889 重新加锁后再次检查 isTerminalStreamStatus，已终态则不启动 provider goroutine；或把 status 检查与 ProviderCancel 赋值合并到同一次锁内原子完成。

#### P1-10 runProviderStream 的 Done 事件回投失败时未保证流进入终态，可能永久卡 streaming（内存泄漏）
- **位置**：[service.go:1100-1144](internal/backend/forwarder/service.go)
- **现象**：若 postErr==errProviderLoopInterrupted，不调 failStream，provider 已结束但流状态仍 streaming（ProviderActive=true），broker 里流永不进终态，RemoveIfIdle 因 ProviderActive=true 不移除 → 流永久驻留 broker，内存泄漏；重连订阅者永远等不到 endstream。
- **修复建议**：postErr==errProviderLoopInterrupted 时在当前 goroutine 兜底把 stream 推进终态（直接调 broker.Fail），不依赖 actor。

#### P1-11 RunSSE 客户端不读时 backlog 堆积到 8192 上限后静默丢非终态事件，agent 输出「断片」
- **位置**：[service.go:275-365](internal/backend/forwarder/service.go)，broker.go:339-352
- **现象**：客户端长时间不读 RunSSE 时 backlog 持续 append 到 8192 上限，超限丢最旧非终态事件；重连从 cursor=0 读丢失中间 text/tool delta。心跳不缓解（问题是客户端不消费而非断连）。
- **修复建议**：慢消费时 stream.Send 阻塞应反压 provider（暂停 Publish）而非丢事件；或超限下发 truncation 提示事件让客户端感知。

#### P1-12 awaitShellBlockUntilMatched 用 time.Sleep 在 actor goroutine 上阻塞，卡死整条流消息处理
- **位置**：[await_shell_tool.go:103-133](internal/backend/forwarder/await_shell_tool.go)
- **现象**：handleAwaitShellToolInvocation 在 runStreamActor 单线程上同步执行，awaitShellBlockUntilMatched 用 time.Sleep 轮询最多 blockUntilMS（默认 30s）。期间该 stream 整个 actor mailbox 被阻塞，所有并发 BidiAppend/interrupt/exec dispatch/provider_event 堆积在容量 128 的 mailbox。注释声称「不阻塞 actor mailbox」与实际相反。
- **修复建议**：阻塞轮询移出 actor goroutine，独立 goroutine 轮询完成后 streamCommand 回投 mailbox 串行完成（参考 runImageGeneration）；用事件唤醒代替 200ms 轮询 sleep。

#### P1-13 block_until_ms 无上限，模型可传任意大值永久卡死 actor
- **位置**：[await_shell_tool.go:84-87, 176-183](internal/backend/forwarder/await_shell_tool.go)
- **现象**：block_until_ms 是模型可控入参，decodeAwaitShellArgs 仅把负数归零无上界。模型传 86400000000 时 deadline 在 ~3 年后，循环一直 sleep。配合 P1-12，stream actor mailbox 被永久占用，流无法取消，stream 对象及全部 maps 无法 GC。
- **修复建议**：加硬上限（如 120000ms）超过截断；循环每轮检查 stream 是否已终态/被取消。

#### P1-14 Stdout/Stderr buffer 尾部截断后 AwaitStdoutOffset 失效，新输出对模型不可见（数据丢失）
- **位置**：[await_shell_tool.go:217-224, 414-466](internal/backend/forwarder/await_shell_tool.go)
- **现象**：appendShellStreamBuffer 超 256KB 时 clampShellBuffer 丢弃头部只留尾部，buffer 逻辑起始字节前移，但绝对偏移 AwaitStdoutOffset 未调整。场景：buffer 已 256KB，snapshot 设 offset=256KB；下一 chunk 10KB 到达，clamp 后新 buffer 仍 256KB 尾部（起点前移 10KB），offset 仍=256KB=len，stdout=buffer[256KB:] 为空——这 10KB 新输出模型永远看不到。长输出命令（构建日志）关键尾部行丢失。
- **修复建议**：clamp 时同步扣减 offset（丢弃 headLen 字节则 offset-=headLen，下溢归 0）；或 BackgroundShellState 记 bufferBaseOffset。

#### P1-15 appendConversationEntries 失败后留脏状态：Phase=Compacting/ProviderActive=true 但无 goroutine 推进
- **位置**：[compaction.go:356-388](internal/backend/forwarder/compaction.go) startPendingCompactionSummary
- **现象**：先在持锁段设置 Phase=TurnPhaseCompacting/ProviderActive=true/ProviderCancel=cancel，解锁后才调 appendConversationEntries。若返回 err，函数 cancel() 并 return err，**未回滚已设置的 ProviderActive/Phase/PendingCompaction**。流卡死在 Compacting 相位，reconcileStream 认为 provider 仍活跃而不恢复。
- **修复建议**：appendConversationEntries 失败时重新加锁回滚 Phase/ProviderActive/PendingCompaction，再 cancel() 返回；或把 appendConversationEntries 移到设置状态之前。

#### P1-16 旧压缩 goroutine 未取消，新旧摘要增量交叉推送致 UI 错乱
- **位置**：[compaction.go:390-414, 416-485](internal/backend/forwarder/compaction.go)
- **现象**：re-entrancy 时 stream.ProviderCancel 被新 cancel 覆盖但旧 cancel 未调用，旧 goroutine 仍在 generateCompactionSummary 向 broker.Publish 推摘要增量，与新一轮交叉推送，UI 摘要文本错乱。
- **修复建议**：覆盖 stream.ProviderCancel 前先调用旧的取消旧 goroutine，确保同一时刻只有一个 compaction 摘要 goroutine 在跑。

#### P1-17 历史轮压缩丢弃全部 tool_result 原文/图片/reasoning signature，仅留 ~300 字符片段
- **位置**：[compaction.go](internal/backend/forwarder/compaction.go) buildContextTurnCompactionCandidate ~L1060-1103，buildCompactedTurnSummary ~L1150-1193
- **现象**：对历史轮，每个 tool_result 仅生成一行摘要截断到 300 字符；之前轮 Read 出的文件内容/Bash 输出/Edit diff 全丢失；图片仅记 `[attached_images=N]` 计数，inline data 丢失；reasoning_content/reasoning_signature 完全不入摘要，跨压缩后无法继续思维链。真实 Cursor 保留结构化片段或更长内容。
- **修复建议**：按工具类型保留更长片段（文件路径、命令、关键返回摘要）；图片以 reference_image_paths 保留；reasoning signature 至少在最近一轮保留。

#### P1-18 压缩无条件选择全部历史轮，无 tail 保留与 token 回收逻辑
- **位置**：[compaction.go:1033-1058](internal/backend/forwarder/compaction.go) buildContextCompactionCandidates
- **现象**：所有非当前轮/非 compaction_summary 轮全部作候选。本应负责按需选择的 selectTurnsForCompaction（含 compactionPreferredTailTurns=4 尾部保留与 reclaimTokens 回收阈值）是死代码（见 P2 死代码项），从未调用。每次自动压缩把本应保留为原文的近期 4 轮也压缩掉。
- **修复建议**：接入 selectTurnsForCompaction 的尾部保留与 token 回收逻辑，只压缩超出 reserve 的最早若干轮。

#### P1-19 buildStartedToolCall 对未知工具名返回 nil，调用方仍以 nil ToolCall 发布 ToolCallStarted
- **位置**：[events.go:535-537](internal/backend/forwarder/events.go)，tool_invocation.go:109-138
- **现象**：default 分支返回 nil，但 tool_invocation.go 在 !bufferExecDispatch && !suppressStartedToolCall 时无条件发送，把 nil *ToolCall 塞进 ToolCallStartedUpdate.ToolCall。客户端收到 CallId 有值但 ToolCall 为 nil 的 started 事件，无法知道是哪个工具，后续关联渲染断裂。
- **修复建议**：Publish 前增加 `if startedToolCall == nil { 跳过或构造 fallback }`。

#### P1-20 Anthropic 流 EOF 无 message_stop 时可能丢失 usage 计费
- **位置**：[anthropic.go:760-769](internal/backend/agent/model/anthropic.go)
- **现象**：emittedAny=true 的 EOF 路径（760-769）执行 flushTaggedTextTail + flushThinkingCompleted + 落盘 summary artifact 后 return nil，**未见发射 TurnFinished 事件**（对比 OpenAI 同路径调 flushTurnFinished）。TurnFinished 是下游 usage 计费/落盘 token 唯一触发点，缺失则这类流的 token 不计入 usage.json。
- **注**：本项子代理报告标注，我已验证 760-769 路径确无显式 TurnFinished 调用，但 recordLLMSummaryArtifact 是否内含 usage 落盘需进一步确认；若已含则降为 P2。
- **修复建议**：在 anthropic.go EOF 收尾处补一次与 OpenAI flushTurnFinished 等价的 TurnFinished 发射，确保 emittedAny=true 的流无论是否收到 message_stop 都向下游发 TurnFinished。
