## 第一部分　cursor-switch 自身不合理之处（按严重度排序）

### 高严重度（High）

#### H1. tab 补全流量硬编码到第三方私有域名 `tab.leokun.cn` ✅ 已修（config 可空禁用回退官方）
- **位置**：`internal/backend/host.go:27`（`tabServerBaseURL = "https://tab.leokun.cn"`）+ `tabServerUpstreamProcedure`（`host.go:382-392`）
- **问题**：`StreamCpp` / `StreamNextCursorPrediction` / `CppConfig` / `WriteGitCommitMessage` / `WriteGitBranchName` 等 tab 补全与 git 消息接口被强制路由到作者私有服务 `tab.leokun.cn`，域名写死在二进制里，UI/config 中无法切换或关闭。用户的代码补全 / git commit 生成流量被默默导向一个非 Cursor 官方、非用户自配的第三方端点。`tabServerUpstreamProcedure` 用 `upstream.DirectAction` 默认 `CredentialNone`——凭证不会泄漏（这点安全），但用户**无法让 tab 补全走自己的 Cursor Pro 额度**，是兼容性损失点。
- **建议**：把 tab server 地址提到 config（可空 = 禁用 tab 重定向，回退到官方 `api2.cursor.sh` 透传）；README 明确说明 tab 流量去向；考虑默认禁用第三方 tab server。配套 `cursor-tab-server/main.go` 支持填用户自己的 cursor token，回源用户账号而非共享池。

#### H2. `update.json` 签名是手动两步流程，CI 默认产出未签名 manifest ✅ 已修（S18/F-11：CI 自动签名，私钥作 secret 注入，零本地操作；姿态降级见第五部分 F-11）
- **位置**：`internal/updater/pubkey.go:18,28-31` + `.github/workflows/release.yml:128-145`
- **问题**：release.yml 注释明确 manifest 是 **UNSIGNED**，需维护者本地跑 `scripts/release sign` 后 `gh release upload --clobber`。`verifyManifestSignature` 在 `releasePublicKeyHex == ""` 时直接 `return true`（仅 checksum 校验）——虽然当前二进制已硬编码公钥，但这个降级分支永远存在。更严重：**签名密钥对的私钥完全离线，无轮换机制**——`releasePublicKeyHex` 是 `var` 但无运行时加载路径，私钥泄露即需重发版强制所有客户端升级。
- **建议**：CI 集成签名（secrets 存私钥）消除手动步骤；引入公钥版本/轮换字段到 manifest；移除"空公钥放行"降级，至少在日志以 ERROR 级告警。1.1.0 已用端到端测试验证当前签名链工作，但流程瓶颈与轮换缺口仍在。

#### H3. relayauth proof 进程级单例隐藏初始化竞态
- **位置**：`internal/relayauth/proof.go:37-53` + `internal/mitm/service.go:191` + `internal/backend/server/middleware.go:67`
- **问题**：`relayauth.New()` 用 `sync.Once` 进程级单例生成 32 字节随机 proof。MITM 侧（`mitm.NewProxyServer`）和 backend 侧（`LoopbackAuth`）**各自独立调用 `relayauth.New()`**，靠"同进程 sync.Once 返回同一实例"侥幸一致。问题：(a) 若未来 MITM 与 backend 拆成独立进程（或测试中分别 `New`），proof 不一致，所有请求 401；(b) `LoopbackAuth` 在 middleware 构造时 `relayauth.New()` 返回的 `err` 被 closure 捕获后**对每个请求都判断**，但 proof 实例是构造时的——若 `rand.Read` 失败，整个 backend 永久 401 且无恢复路径；(c) proof 随进程重启变化但无持久化，重启后任何 in-flight 的 MITM→backend 请求失败。
- **建议**：显式把 proof 作为依赖注入到 MITM 和 backend（而非两个 `New()` 靠单例耦合）；构造期失败应 fatal 而非每请求判断；文档化"同进程"前提。

#### H4. `GetThoughtAnnotation` 全量扫描所有会话所有 entry —— O(会话数 × entry 数) 性能炸弹 ✅ 已修（requestID→entry 反向索引）
- **位置**：`internal/backend/forwarder/ai_handler.go:181-241`
- **问题**：`lookupThoughtAnnotation` 调 `ListConversationIDs()` 后对每个 conversation `LoadConversation`（读盘 + 反序列化整个 JSON），再遍历所有 entry 找匹配 `requestID` 的 `thought_annotation`。这是 Cursor 客户端每个 agent turn 收尾时高频调用的接口。会话积累到几百条后，单次调用要读几百个 JSON 文件并反序列化全部 entry。**这是明确的潜在 bug/性能缺陷**，会在长期使用后导致 UI 卡顿。
- **建议**：建 `requestID → (conversationID, entryIndex)` 反向索引；或把 `thought_annotation` 单独写到 sidecar 文件按 `requestID` 寻址。

#### H5. usage.json 500 条截断导致 turn 计费漏算 ✅ 已修（EventIndex 独立持久化）
- **位置**：`internal/backend/forwarder/usage_store.go:132-180`
- **问题**：每次 provider 事件 `UpsertEvent` 都：acquireConversationLock → 读全文件 → 反序列化 → 修改 → 原子写回。在高频多会话场景（agent 多工具循环），所有 token 计费串行化在这个锁上。同时 `doc.EventIndex` 与 `doc.RecentEvents` 是同一数据的两份表示，`trimRecentUsageEvents` 把 RecentEvents 截断到 500 后 `buildUsageEventIndex` 重建索引——**意味着超过 500 条旧事件的 EventIndex 丢失**，`LookupEvent` 对旧 requestID 查不到，`recordTurnFinalizedSnapshot`（`token_usage.go:386-410`）聚合 turn 时拿不到旧 provider_call 的 token，**turn_finalized 事件 token 字段为 0**，导致 `usageTurnStatusDone` 但无 token——计费漏算。
- **建议**：EventIndex 不依赖 RecentEvents 截断（独立持久化或用真正索引文件）；写路径改 append-only log + 定期 rollup；评估 SQLite（cc-switch 已用 rusqlite bundled，可对齐）。

### 中严重度（Medium）

#### M1. `realTotalTokens` 对 TOTAL 语义重复计 cache（计费/展示 bug） ✅ 已修（按 InputTokenSemantics 修正）
- **位置**：`internal/bridge/dashboard.go:166-170` + `usage_store.go:151`（`event.TotalTokens = input+output+cacheRead+cacheWrite`）
- **问题**：`usageFileEvent.TotalTokens`（store 层）与 `RealTotalTokens`（dashboard 层）用**完全相同的公式** `input+output+cacheRead+cacheWrite`，只是名字不同。`usageFileTotals.TotalTokens` 也是同公式。三处同义字段并存，前端 `UsageDashboard.vue` 同时展示 `totalTokens` 和 `realTotalTokens`，用户无法区分。更危险：对 `InputSemanticsTotal`（OpenAI gpt-5.x）模型，`input` 已含 `cacheRead+cacheWrite`，此时 `realTotalTokens = input+output+cacheRead+cacheWrite` 会**把缓存部分计 3 次**（input 里 1 次 + cacheRead 1 次 + cacheWrite 1 次）。注释说"参考 cc-switch derive_real_total"，但 cc-switch 对 TOTAL 语义会先 `input - cacheRead - cacheWrite` 再加，这里没做。
- **建议**：`realTotalTokens` 按 `InputTokenSemantics` 调整（TOTAL 时 `fresh_input = input - cacheRead - cacheWrite`）；统一 `TotalTokens` / `RealTotalTokens` 或明确文档化差异。这是 1.1.0 daily 精确化之后下一个该做的计费修正。
- **2.0.4 更新（根治）**：2.0.0 的修复让 `realTotalTokens`/`billableInputTokens` 按 seed 标注的语义正确折算，但暴露了更深的**数据契约矛盾**——adapter 落盘的 input 实际已是 fresh_input（Anthropic 原样存 API 的 `input_tokens`，本就只算非缓存部分；OpenAI 存 `prompt_tokens - cached_tokens`），所有 OpenAI 兼容 provider 经 openai.go 同一条路全是 fresh。但 seed 把 OpenAI 标 TOTAL、Anthropic 标 legacy，与落盘口径矛盾 → TOTAL/legacy 分支对 fresh 数据重复扣 cache（成本低估）+ `isCalibrationAnomaly` 持续误报 487 条。**2.0.4 把内置 seed 全标 FRESH 对齐落盘口径**（等价 cc-switch SQL fresh_input 归一化），并加 `normalizePricingConfig` 迁移把老用户磁盘配置残留的 TOTAL/legacy 内置记录迁到 FRESH。`realTotalTokens`/`billableInputTokens`/`isCalibrationAnomaly` 计算分支不动，仅 seed 标注 + 迁移。3 测试锁定（seed 全 FRESH / 迁移保留价格 / 禁用记录也迁）。详见 release-notes 2.0.4。

#### M7. MITM CA leaf 证书 RSA-2048 且缓存无 TTL/失效机制 ✅ 已修（ECDSA P-256 + TTL/过期重签）
- **位置**：`internal/certs/ca.go:110`（`rsa.GenerateKey(rand.Reader, 2048)`）+ `ca.go:140`（cache 永久）
- **问题**：每 host leaf 证书 RSA-2048，缓存 `map[string]*tls.Certificate` **永不过期**（leaf NotAfter 是 1 年，但 cache 不检查）。长期运行进程 1 年后 leaf 过期但 cache 仍返回过期证书——**MITM 握手会用过期证书**，Cursor 客户端报证书错误。RSA-2048 签发也偏慢（goproxy 已有 `mitmCertStore` 缓存，但 ca.go 自己又缓存一份，两套缓存）。CA 本身 RSA-4096（ca.go:254）合理，但 leaf 用 RSA 而非 ECDSA 导致每次新 host 签发延迟。
- **建议**：leaf 改 ECDSA P-256（更快、更小）；cache 检查 NotAfter，过期重签；统一 `mitmCertStore` 与 ca.go cache。

#### M8. `EnsureMachineCA` 在"文件存在但解析失败"时静默备份重建 ✅ 已修（S19/F-12：损坏备份 .corrupt.bak 后重生 + CA 校验）
- **位置**：`internal/certs/ca.go:248-252`
- **问题**：`loadCAPEMFromFiles` 失败且非 NotExist 时，`os.Rename` 到 `.corrupt.bak` 后直接重新生成 CA。新 CA 与旧 CA 完全不同——**所有由旧 CA 签发的 leaf 证书（含 Cursor 客户端已信任的）全部失效**，用户需重新信任 CA。这是静默操作，用户无感知。若 CA 文件因磁盘错误临时损坏，本可恢复却直接重建。
- **建议**：损坏时 fail 并提示用户手动恢复；或先尝试从 `.corrupt.bak` 恢复；至少日志 ERROR 级告警。

#### M9. cost 计算的 `billableInputTokens` 与 `realTotalTokens` 口径不一致 ✅ 已修（成本口径异常检测提示）
- **位置**：`internal/bridge/metrics.go:336-352` + `dashboard.go:168-170`
- **问题**：TOTAL 模型若 provider 返回的 `input` 未正确包含缓存（某些 OpenAI 兼容第三方返回口径不准），`billableInputTokens` clamp 到 0（漏算 input 成本），但 `realTotalTokens` 仍用原 `input+...`（虚高 token 数）。两个指标对同一数据给出矛盾信号：成本偏低，token 偏高。无校验或告警。
- **建议**：检测 `input < cacheRead+cacheWrite` 时标记为"口径异常"并在 UI 提示；统一 clamp 策略。
- **2.0.4 更新（误报根除）**：2.0.0 的异常检测 `isCalibrationAnomaly`（TOTAL→`input < cacheRead+cacheWrite`，legacy→`input < cacheRead`）逻辑本身正确，但它基于「seed 标注的口径 = 落盘口径」这一前提——而此前 seed 标注与 adapter 落盘口径矛盾（见 M1 2.0.4 更新），导致对 fresh 落盘数据，TOTAL/legacy 分支几乎恒判异常 → 持续红字「⚠ 487 条口径异常」。2.0.4 把 seed 全标 FRESH 后，`isCalibrationAnomaly` 走 FRESH 分支恒返回 false，误报清零。**结论**：M9 的检测逻辑保留（对真正接了未归一 provider 的自定义模型仍有效），但内置 seed 不再触发它——因为 adapter 落盘已统一 fresh，内置模型口径正确无误报。

#### M10. `loopbackAuthExemptPath = "/healthz"` 硬编码，与 host.go `healthPath` 用注释维持一致
- **位置**：`internal/backend/server/middleware.go:56` + `internal/backend/host.go:25`
- **问题**：两处常量靠注释"保持一致"，无编译期保证。若 healthPath 改了，LoopbackAuth 会拦截健康检查，导致 `HealthCheck` 失败误判后端宕机。
- **建议**：单一常量源；或 middleware 接受 exempt paths 参数注入。

## 第二部分　走自建本地路由相对 Cursor 官方路由的能力损失

> **重要前提更正**：旧版（≤0.0.41）"本地 mock 伪造无限制 Pro / marketplace 能看不能装"的问题在 1.0.0 三条控制面分离后**已修复**：身份/marketplace/auth 面官方透传，真实账号与 byok 共存；marketplace/customize/plugins/MCP/skills/rules/commands/hooks 全功能可用。订阅面 mock 仅用于解锁模型选择器不被 `allowedModelIds` 锁 auto。真正的损失集中在**推理面被迫本地重建 Cursor 专有 agent 协议**带来的兼容性缺口。

### 损失盘点（逐项）

#### L-1. Tab 补全（Copilot 式行内建议）——走第三方共享池
- **Cursor 官方**：行内 Tab 补全（`StreamCpp` / `StreamNextCursorPrediction` / `CppConfig` / `RefreshTabContext` 等 cursor 专有小模型端点）。
- **当前处理**：透传到第三方 `tab.leokun.cn`（`host.go:tabServerUpstreamProcedure`），`CredentialNone`；由独立的 `cursor-tab-server/main.go` 用单独 token 转发到 `api2/3/4.cursor.sh`。
- **损失程度**：中。Tab 补全**仍可用**，但走的是**作者托管的 `tab.leokun.cn` 中转 + 共享 token**，而非用户自己的 Cursor 账号。(a) 质量取决于该中转服务可用性与 token 额度；(b) 用户真实 Cursor 订阅里的 Tab 额度**不被使用**（凭证隔离，`CredentialNone`）；(c) `CppService/*` 兜底返回 404（`host.go:425`）。
- **根因**：Tab 用的是 cursor 专有端点，无法用 byok provider 替代（小模型是 cursor 自家），只能中转回官方；作者选择集中托管而非每用户配自己的 cursor token。
- **缓解**：让 `cursor-tab-server` 支持填入**用户自己的 cursor token**（当前 `config.yaml` 只有一个 `token` 字段，且默认从 `config.example.yaml` 复制），把 Tab 流量回源到用户本人账号而非共享池。

#### L-2. codebase 索引 / @codebase 检索——本地简化重建
- **Cursor 官方**：`@codebase` 语义检索（`RepositoryService/*` 的 merkle 子树同步 + `AiService/CreateExperimentalIndex` 等）。
- **当前处理**：本地完全重建（`forwarder/codebase_index_handler.go` + `codebase_index_store.go` + `repository_index_handler.go`）。`EnsureIndexed` / `ListFiles` / `ListenExperimentalIndex` / `RegisterFileToIndex` 全部本地实现，`RepositoryServiceFastRepoInitHandshake` / `SyncMerkleSubtree` 等也本地处理。
- **损失程度**：中-高。@codebase **可工作**，但是本地简化版：(a) 没有 cursor 云端的语义嵌入向量索引（本地是文件哈希 + 注册表，`codebaseFileContentHash` 是 sha256，不是 embedding）；(b) `ListenExperimentalIndex` 只回放 `register` 事件，无真正的向量检索；(c) 检索质量取决于 byok 模型对上下文的处理，而非 cursor 的专有 RAG。
- **根因**：cursor 的 codebase 索引是云端专有 RAG（嵌入 + 向量库），byok 无法把用户代码上传到 cursor 云（凭证隔离 + 隐私），只能本地重建；但本地重建停留在"文件清单 + 内容注入"层级，未实现向量检索。
- **缓解**：(1) 本地接轻量 embedding 模型（如本地 ollama embedding）做向量检索；(2) 或对 `RepositoryService/*` 提供"透传到用户本人 cursor 账号"的可选模式（仅该面用真实凭证），让索引仍走 cursor 云。

#### L-3. agent 模式（apply / edit / run-command / terminal）——本地重建，最完整
- **Cursor 官方**：agent 的 tool use：Read/Write/Edit(PatchEdit)/Shell/Task/MCP/Grep/Glob/Ls/TodoWrite/WebFetch/WebSearch 等。
- **当前处理**：本地完全重建 agent 执行循环（`forwarder/actor.go` 的 stream actor + `agent/bridge/exec/bridge.go` 的 exec 桥）。解码 cursor 的 `AgentClientMessage` proto（hex 编码的 BidiAppend），把 tool call 映射成 `AgentServerMessage_ExecServerMessage` 发回 cursor 客户端执行，再把 `ExecClientMessage` 结果摘要回写给 byok 模型。
- **损失程度**：低-中。这是本项目**投入最大、做得最完整**的部分：tool catalog（`tool_catalog.go`）含 `PatchEdit`/`AwaitShell`/`ForceBackgroundShell`/`SwitchMode`/`Task`（subagent）全套；shell 流式、后台 shell、写路径围栏、MCP 调用都本地实现。缺口：(a) 工具的**具体行为依赖 cursor 客户端**本地执行（Read/Write/Shell 实际由 cursor IDE 跑），forwarder 只做协议桥接——若 cursor 客户端版本更新 proto 字段，本地桥需同步跟进；(b) `actor.go:527` 对 OpenAI Responses 的加密 thinking 用占位文本 "Thinking is encrypted..." 兜底，说明对 cursor 的 thinking 加密协议支持不完整。
- **根因**：agent 协议是 cursor 专有 proto（`agentv1`），byok 必须在中间重实现一套兼容层；该兼容层永远滞后于 cursor 官方 proto 演进。
- **缓解**：持续跟随 cursor proto 版本（项目已硬编码支持到 Cursor 3.9.16，见 release-notes）；补齐 OpenAI Responses 的 reasoning signature 加密回传，避免占位文本。

#### L-4. chat 模式 / @file @web @docs 上下文——本地重建，@docs 覆盖窄
- **Cursor 官方**：chat 的 @file（文件上下文）、@web（联网搜索）、@docs（文档检索）。
- **当前处理**：本地重建：`@file` → `CountTokens`/`ContextItem` 本地处理（`ai_handler.go`）；`@web` → 暴露 `WebFetch`/`WebSearch` 工具（`tool_catalog.go`）；`@docs` → `DocumentationQuery`/`AvailableDocs`/`KnowledgeBase*`/`UploadService/*` 本地实现（`docs_index_handler.go` + `upload_docs_handler.go`）。
- **损失程度**：中。@file 正常；@web 走 byok 模型的工具调用（取决于 provider 是否支持 web tool）；@docs 是**本地文档库**（`docs_index_store.go`），不是 cursor 云端文档索引，覆盖范围远小于 cursor 官方 @docs（后者预索引了大量第三方库文档）。
- **根因**：@docs 的价值在 cursor 云端预建的文档向量库，本地无法复制；@web 依赖模型 tool use 能力。
- **缓解**：@docs 可考虑透传 `UploadService/*` 到用户本人 cursor 账号（仅该面用真实凭证），复用云端文档索引。

#### L-5. prompt cache / conversation history / checkpoint/undo——本地实现且较完整
- **Cursor 官方**：prompt 缓存、会话历史持久化、checkpoint/undo。
- **当前处理**：本地实现且较完整：prompt cache 在适配器层（`anthropic.go:applyAnthropicCacheBreakpoints` 注 `cache_control: ephemeral`；`openai.go:openAIPromptCacheKey` 注 `prompt_cache_key`）；历史持久化到 `~/.cursor-local-assistant-v2/`（`history_maintenance.go`）；checkpoint 在 `actor.go:publishCheckpoint` + `checkpoint_memory.go`；rewind/undo 在 `rewind.go`（`runRewindDecision.Apply`）。
- **损失程度**：低。这是兼容得最好的部分——prompt cache 命中率甚至比 cursor 官方更可控（用户可调 breakpoint）。缺口：(a) cursor 官方的 cross-session cache 可能更激进；(b) `GetThoughtAnnotation`（`ai_handler.go:105`）对 thinking 摘要的回查是本地存储，找不到时返回空或 `defaultSummaryCompletedThought` 兜底，cursor UI 的 thinking 折叠可能显示不全。
- **缓解**：无需大改；`GetThoughtAnnotation` 的兜底可改进为从 provider 原始 reasoning 流回放。

#### L-6. Cursor Bugbot / 评审 / 后台任务——云端一体化，端到端断裂
- **Cursor 官方**：Bugbot（PR 评审）、background composer、后台 agent 任务。
- **当前处理**：混合：`BackgroundComposerService/*` 官方透传（`host.go:617`）；`BackgroundTaskCompletionAction` 本地处理（`await_shell_tool.go:746`，仅 shell 类后台任务）；但 Bugbot 的**推理部分**会走 byok（因为推理面被接管）。
- **损失程度**：中-高。Bugbot 是 cursor 云端托管的异步任务（在 cursor 服务器跑、用 cursor 的模型 + 仓库索引），byok 把推理面接管后，Bugbot 若触发推理会走 byok provider——但 Bugbot 的调度入口、通知、PR 集成是 cursor 云端逻辑，本地无对应实现。**结果：Bugbot 大概率不可用或行为异常**。
- **根因**：Bugbot 是 cursor 云端一体化服务（调度 + 推理 + 索引），不能拆分；byok 只接管推理面，破坏了其端到端假设。
- **缓解**：对 Bugbot 相关请求**整体透传到用户本人 cursor 账号**（用真实凭证），不接管其推理；或在文档明确声明 Bugbot 不支持。

#### L-7. 模型选择器 / fast/slow 模型切换——本地 mock（刻意设计，非损失）
- **损失程度**：低（这是**特意设计的目标**，非损失）。用户能选自己的 byok 模型，不被锁 auto。重构记录的"坑 5/7/8"专门解决了锁 auto 问题。
- **缓解**：无需改；可考虑让 `auto` 映射到用户配置的"默认通道"。

#### L-8. 真实账号登录态 / marketplace / MCP / skills / subagents / rules / commands / hooks——官方透传（已修复）
- **损失程度**：**极低（已修复）**。旧版"能看不能装"的问题在 1.0.0 通过整条 marketplace 链改透传解决（重构记录坑 1/2）。唯一残留：`stripe_profile`/`full_stripe_profile`/`has_valid_payment_method` 仍本地 mock（`host.go:556-603`），但这只影响订阅状态显示，不影响 marketplace 功能。
- **缓解**：无需改；stripe mock 必须保持与套餐 mock 一致（重构记录坑 8：否则触发轮询风暴 + 锁 auto）。

### 损失根因分析

- **根因 A：推理面强制本地重实现 cursor 专有 agent 协议**。byok 把 `BidiAppend`/`RunSSE`（`agent.v1.AgentService`）整体接管到本地 forwarder。这些是 cursor 专有 Connect-RPC + hex-proto 流式协议，本地必须维护入站解码（`protocol/inbound.go` 的 `AgentClientMessage` oneof 分支）、执行桥（`exec/bridge.go` 14 种工具的 proto 映射）、出站事件（`actor.go` 的 `buildTextDeltaMessage`/`buildPartialToolCallMessage` 等）。任何 cursor proto 字段演进都需要本地跟进，否则能力降级。这是**协议兼容性滞后**问题，不是分类错误。
- **根因 B：byok provider 不支持 cursor 专有协议扩展**。cursor 的 thinking 加密、`reasoning_signature`、特定 tool use 格式，在第三方 OpenAI/Anthropic 兼容 API 上没有等价物。`actor.go:504-530` 对 OpenAI Responses 的加密 thinking 用占位文本兜底；`anthropic.go` 的 `cache_control` 注入是对 Anthropic 原生能力的复用，但 cursor 的 `GetThoughtAnnotation` 摘要回查（`ai_handler.go:181`）是本地存储，无法还原 cursor 云端的 thinking 处理。
- **根因 C：mock 订阅面与透传身份面的刻意不一致（已知且已解决，但留有边界）**。重构记录坑 8 的核心洞察：身份透传（真实）+ 套餐 mock（无限制）= 潜在不一致。当前通过"严格分区"解决——`GetMeResponse` 不含套餐字段所以透传安全，stripe 三接口必须 mock 以保持一致。但这个**不变量很脆弱**：任何新增的、同时携带身份和套餐字段的 cursor 接口，若误归到透传面，会重新触发轮询风暴/锁 auto。这是**架构脆弱性**，不是当前 bug。

### 如何更契合 Cursor（按可行度排序）

#### 优先级 1（高可行度，低风险）：把"云端一体化服务"整体透传，不拆推理面
- **问题**：Bugbot、Tab 补全、@docs 文档索引、codebase 向量检索都是 cursor 云端一体化服务，byok 拆走推理面就破坏了它们的端到端假设。
- **方案**：对这些服务的请求**整体透传到用户本人 cursor 账号**（`CredentialOriginalCursor`），不让 byok 接管其推理。具体：`RepositoryService/*`（codebase 索引）改为可选透传到用户 cursor 云端（牺牲隐私换召回质量）；`UploadService/*`（@docs 文档）同上；Tab 补全的 `tab.leokun.cn` 改为支持填用户自己的 cursor token，回源用户账号；Bugbot 相关整体透传。
- **代价**：用户代码/文档会上传到 cursor 云端（需用户知情同意）。但这是"更契合 Cursor"的最直接路径——这些能力本来就是 cursor 云端专长。
- **实现位置**：`host.go` 的 `repositoryServiceProcedure`/`uploadServiceProcedure` 增加 `CredentialOriginalCursor` 透传分支，由配置开关控制。

#### 优先级 2（高可行度）：配置层细粒度路由选择 ✅ 已实现（2.0.3）
- **问题**：当前 `Routing.Mode`（`config/types.go:50`，`manager.go:174`）是**全局开关**——要么全 local（byok），要么全 upstream（直连 cursor）。`PolicyMiddleware`（`middleware.go:48`）对每个请求统一设 `ctx.Mode`，无法按路由/按模型选择。
- **方案**：把路由模式从全局细化为**按面配置**：推理面（RunSSE/BidiAppend）始终 byok；云端一体化服务（codebase/docs/bugbot/tab）可选 byok 本地重建或透传用户账号；身份/marketplace 始终透传；套餐/用量始终 mock。在 `Routing` 配置里增加 per-namespace 的模式覆盖（如 `routing.codebase: passthrough|local`），`PolicyMiddleware` 按路由名查表而非全局读 `Mode`。
- **实现（2026-07-28）**：`RoutingConfig` 加 `PerNamespace map[string]string`（key=route name，value=`local`/`upstream`，未列出=跟随全局）。`normalizePerNamespace` 清洗非法值/空值并丢弃"auto"（等价不覆盖），全空返回 nil 向后兼容旧配置无此字段。`Manager.RouteModeFor(hasUpstreamURL, routeName)` 优先查覆盖表回退 `RouteMode`。`PolicyMiddleware` 改用 `RouteModeFor(ctx.UpstreamURL != nil, ctx.RouteName)`——`ctx.RouteName` 本就每请求由 `newContext` 从 `route.Name` 填充，无需新管道。`shouldUseUpstreamAction` 去掉 `_ = route`（决策已落到 ctx.Mode）。前端 Config.vue 加「按路由面覆盖」面板：cpp_service/file_sync/network_service 三条高价值路由各一 Select（跟随全局/本地 byok/直连 Cursor），`savePerNamespaceRoute` 单条保存；推理面（run_sse/bidi_append/ai_service）刻意不暴露——强制本地是项目目标。11 测试（7 config 层 normalize/RouteModeFor/NormalizeConfig 往返 + 4 PolicyMiddleware 按路由分流/native 恒 local/覆盖双向/空 RouteName 回退）。
- **实现位置**：`internal/backend/server/config/types.go` 扩展 `Routing` 结构；`middleware.go:PolicyMiddleware` 改为按路由查表。

#### 优先级 3（中可行度）：完善 byok 推理面的 agent 协议兼容层
- **方案**：补齐 OpenAI Responses 的 `reasoning_signature` 加密回传（当前 `actor.go:527` 用占位文本），让 cursor UI 的 thinking 折叠正常工作；`GetThoughtAnnotation`（`ai_handler.go:181`）改为从 provider 原始 reasoning 流回放，而非本地存储兜底；持续跟随 cursor proto 版本（`agentv1`/`aiserverv1` 的 gen 代码再生成）。
- **实现位置**：`internal/backend/agent/model/openai_responses.go` + `forwarder/ai_handler.go`。

#### 优先级 4（中可行度）：mock 面从"静态 mock"升级为"智能透传+改写"
- **方案**：把静态 mock 升级为**透传+字段改写**——先透传到用户真实 cursor 账号拿真实套餐数据，再在响应里把 `allowedModelIds`/`allowedModelTags` 清空、把用量置零。这样既保持"无限制解锁"语义，又自动跟进 cursor 新字段，避免 mock 滞后。
- **实现位置**：`internal/backend/server/upstream/mocks.go` 的 `DashboardUsageLimitStatusAndActiveGrantsMockBuilder` 等改为"透传+改写"模式（新 `Credential` 策略 `CredentialOriginalCursorWithRewrite`）。
- **注意**：stripe 三接口**不能**用此方案——重构记录坑 8 明确：stripe 透传真实套餐与用量 mock 矛盾会触发轮询风暴。stripe 必须保持纯静态 mock。

#### 优先级 5（低可行度，长期）：本地补齐 codebase 向量检索
- **方案**：本地接轻量 embedding 模型（ollama embedding 或用户 byok provider 的 embedding 端点），在 `codebase_index_store.go` 里建本地向量库，`ListenExperimentalIndex`/检索时做向量召回。
- **代价**：实现复杂度高；不如优先级 1 的"透传 cursor 云"省事。

## 第三部分　对照 cc-switch 与 CodexPlusPlus 的可借鉴功能

### A. 来自 cc-switch（多工具切换器，本地代理路由同源）

#### A1. 熔断器（Circuit Breaker）+ 故障转移队列（Failover Queue）—— 生产级路由的关键缺失件 ⭐
- **位置**：`cc-switch/src-tauri/src/proxy/circuit_breaker.rs` + `provider_router.rs` + `failover_switch.rs`
- **描述**：每 (app_type, provider_id) 一个熔断器，状态 Closed/Open/HalfOpen，可配 failure_threshold、success_threshold、timeout_seconds、error_rate_threshold、min_requests。`select_providers()` 自动跳过已熔断供应商。故障转移队列：用户拖拽排序一组 provider 形成 P1→P2→… 队列，请求按序尝试，直到成功，与熔断器联动。
- **借鉴价值**：cursor-switch 若只有"失败重试"而无熔断，会在一个挂掉的 endpoint 上反复重试浪费时间。熔断器 + 半开探测是生产级故障转移的关键。多账号场景下"主号挂了自动用副号"。
- **移植难度**：中。Go 侧可用 `sony/gobreaker` 或手写。

#### A2. 请求级 header 大小写保留（wire-level 伪装）⭐
- **位置**：`cc-switch/src-tauri/src/proxy/server.rs`（preserve_header_case）+ `hyper_client.rs` 的 `HeaderCaseMap`
- **描述**：手写 hyper accept loop 捕获客户端原始 header 大小写，转发到上游时还原 wire-level casing，让"被代理的请求"和"直连请求"在 wire 上无法区分。
- **借鉴价值**：Cursor 官方可能基于 header 大小写做指纹识别/风控；保留原样降低被识别为代理的概率。Go 用 `net/http` 默认会 canonicalize header，需手动处理（fasthttp 或自定义 Transport）。
- **移植难度**：高。

#### A3. Thinking Signature 整流器（自愈式重试）
- **位置**：`cc-switch/src-tauri/src/proxy/thinking_rectifier.rs` + `thinking_optimizer.rs` + `thinking_budget_rectifier.rs`
- **描述**：上游返回 thinking signature 校验失败时，自动剥离 thinking/redacted_thinking block 和 signature 字段后重试，修复 Anthropic 风格 API 的签名错误。
- **借鉴价值**：cursor-switch 走 Anthropic 兼容路由时同样会遇到 thinking signature 问题（见第一部分 M5/L-3）；这种"错误触发→自动整流→重试"的自愈模式比直接报错给用户好得多。
- **移植难度**：中。

#### A4. Cache 注入器（强制启用 prompt cache）
- **位置**：`cc-switch/src-tauri/src/proxy/cache_injector.rs`
- **借鉴价值**：降低 cursor-switch 用户成本；这是 prompt cache 处理的核心。cursor-switch 已在适配器层做 `cache_control` 注入，可对齐增强。
- **移植难度**：中。

#### A5. Model Mapper（三维度模型映射）
- **位置**：`cc-switch/src-tauri/src/proxy/model_mapper.rs` + `providers/copilot_model_map.rs`
- **描述**：DB 里同时存 `model`(真实) / `request_model`(客户端别名) / `pricing_model`(计价基准) 三个维度。
- **借鉴价值**：Cursor 自定义模型名常与上游真实模型名不一致，三维度记录让"接管计费可审计"。cursor-switch 当前 model_pricing_candidates 做候选匹配，可对齐三维度记账。
- **移植难度**：中。

#### A6. Live Takeover 备份/还原 + 切换锁 ⭐
- **位置**：`cc-switch` `proxy_live_backup` 表 + `proxy_config.live_takeover_active` + `switch_lock.rs`
- **描述**：接管时把用户原始 settings.json 备份到 DB，退出时原子还原；崩溃也能恢复。切换 provider 时的并发锁，防半切换状态。
- **借鉴价值**：cursor-switch 若直接改 settings.json 而不备份，崩溃后用户配置丢失。这个"接管前备份→退出还原→崩溃恢复"是必须有的安全网。
- **移植难度**：低-中。

#### A7. 定价链增量（cursor-switch 已移植部分 + 未移植部分）
- **`model_pricing_candidates` 7 段剥离**：`cc-switch/services/usage_stats.rs:2094`。依次剥离：known namespace（`anthropic.`/`openai.`/`google.`/`bedrock.` 等前缀）→ claude-desktop 非 Anthropic 前缀（`claude-gpt-...`→`gpt-...`）→ bedrock 版本后缀（`-v1`）→ ISO 日期后缀（8 位/6 位带月日校验）→ reasoning effort 后缀（`-low/-medium/-high/-xhigh/-minimal`）→ claude 点号转横线。BFS 生成全部候选依次查表。**cursor-switch 需确认这 7 段剥离是否齐全**，否则会漏掉大量变种（如 `anthropic.claude-sonnet-4-5-20250929`、`claude-gpt-5`、`gpt-5.6-high`）。
- **`input_token_semantics` SQL 归一化**：`cc-switch/services/sql_helpers.rs` `fresh_input_sql()` + 常量 `LEGACY=0/TOTAL=1/FRESH=2`。提供**跨 provider 聚合时的 SQL CASE 表达式**：legacy 行只减 cache_read，total-inclusive 行减 cache_read+cache_creation，fresh 行不变。`CACHE_INCLUSIVE_APP_TYPES` 显式列出 codex/gemini/grokbuild。**这是"混用多 provider 时 input 口径不一致导致 cache hit rate 失真"的根治方案**。cursor-switch 的 M1 缺口正是这个。
- **`pricing_model_source`**：`cc-switch/proxy_config.pricing_model_source` ('response'/'request') + `proxy_request_logs.pricing_model`。区分"按请求里的模型计价" vs "按响应里的模型计价"，并单独存 `pricing_model` 列做回填。
- **provider 级 `cost_multiplier`**：每个 provider 可设成本倍率（中转商加价 1.1x/1.2x），只作用于最终总价，不污染分项。Decimal 高精度计算（`rust_decimal`）。
- **provider 级日/月限额**：`limit_daily_usd` / `limit_monthly_usd`。多账号预算控制。
- **v3.18.0 内置定价表**：含 Claude Fable 5/Mythos 5、Opus 4.8/4.7、Sonnet 5、GPT-5.6 Sol/Terra/Luna（含 cache write 1.25× 注释）、GPT-5.5/5.4/5.2/5.1/5 全 effort 后缀、Gemini 3.5/3.1/3、DeepSeek V4、Kimi K2.7/K3、GLM-5.2、Qwen3.7、Grok 4.5 等。**cursor-switch 需确认定价表是否同步到这个版本**（尤其 GPT-5.6 cache write 不再免费、Kimi K3、Fable 5）。
- **v7→v8 修正国产模型 CNY→USD 误存**：历史上误把 CNY 值存进 USD 字段，迁移时统一修正 13 个国产模型。**提醒 cursor-switch 检查是否有同类历史脏数据**。

#### A9. 双数据源：代理日志 + 会话日志解析（无代理模式 fallback）

### B. 来自 CodexPlusPlus（Tauri Rust 桌面应用，Codex/ChatGPT 外挂增强壳）

> 与 cursor-switch 工程问题域高度相似（都是"官方桌面应用的外挂式增强壳"），但实现路径不同（CDP 注入 + 本地 HTTP 代理 vs Wails Go 桌面代理）。

#### B1. 协议转换 + 路由一体化代理（直击"路由损失"问题）⭐⭐
- **位置**：`CodexPlusPlus/crates/codex-plus-core/src/protocol_proxy.rs`（`handle_responses_proxy_request` L918、`responses_to_chat_completions` L133、`ChatSseToResponsesConverter` L350）
- **描述**：本地起一个 HTTP 代理（端口 57321），官方客户端发的 Responses 请求被拦下，按当前供应商 `RelayProtocol` 决定是直透还是转 Chat Completions，发上游；上游 SSE 流式回包时用 `ChatSseToResponsesConverter` 边收边转回 Responses SSE 给客户端。客户端完全感知不到后端换了协议/供应商。这是"路由损失"问题的**正面解法**——损失发生在协议转换层，但他们把转换做成了双向全双工 SSE 流式转换，而不是攒包后转。`ChatSseToResponsesConverter` 处理 UTF-8 边界（`utf8_remainder` 缓冲不完整多字节字符，L377）、按 SSE block 切分、状态机维护上下文——这些是流式协议转换的硬骨头。
- **借鉴价值**：cursor-switch 如果也要做"官方协议 vs 自建路由"兼容，这套"协议双向转换器 + 流式 SSE 增量转换"是最值得抄的核心。
- **移植难度**：高。CodexPlusPlus 是"拦截 Responses→转 ChatCompletions"；cursor-switch 的 Cursor 协议形态不同，需要重写转换映射，但状态机骨架和 SSE 分块/UTF-8 处理逻辑可直接复用思路。

#### B2. 聚合供应商轮转 + 故障转移候选链 + 会话粘性
- **位置**：`CodexPlusPlus/crates/codex-plus-core/src/relay_rotation.rs`（`RelayRotationSelector` L77、`select_relay_for_request` L190、`fallback_relays_after` L232）
- **描述**：4 种 `AggregateRelayStrategy`——`Failover`、`ConversationRoundRobin`（会话级粘性）、`RequestRoundRobin`、`WeightedRoundRobin`（带权重）。带故障转移候选链 + 诊断日志。先 `select_relay_for_request` 选主供应商，再 `fallback_relays_after` 算出剩余候选顺序，for 循环逐个尝试，连接失败或非 2xx 自动 failover 到下一个。`ConversationRoundRobin` 用 `conversation_assignments: HashMap<conversation_id, relay_id>` 做会话级粘性（同一对话固定走同一供应商）。
- **借鉴价值**：cursor-switch 做 byok 路由时，"多供应商故障转移 + 会话粘性 + 权重"是直接可抄的成熟设计。会话粘性这点对 agent 场景尤其重要（同一对话换供应商会丢上下文）。
- **移植难度**：中。纯逻辑、无外部依赖，Go 里抄一个等价 selector 即可。与 A1 互补：A1 是熔断（保护），B2 是轮转（分配）。

> **进度（2026-07-27）**：本期实现 **Failover 策略** + A1 接入。
> - `ResolveAdapterIndexes` 复数版（不再"多命中即拒绝"，返回全部候选）
> - `SelectChannelsForModel` 复数版（按 `Priority` 升序稳定排序，`Enabled=false` 不进候选链）
> - `ModelAdapterConfig` 新增 `Priority`/`Enabled`/`Weight` 字段（`Weight` 预留）
> - Router `Stream` failover 循环 + `applyChannelToRequest` 抽取 + `isRetryableChannelError`（5xx/429/连接层 `*url.Error`/流 idle 超时可重试，4xx 透传）+ sink wrapper（`sinkStarted` 闸门，已首字节绝不 failover）
> - `CircuitBreakerRegistry` 注入 `NewProviderGateway`→`NewRouter`，熔断候选排末尾兜底
> - 前端 `ModelEditor.vue` 优先级/权重/启用 UI、`ModelConfig.vue` 候选链徽章
> - **未实现**（留后续）：`ConversationRoundRobin`（会话粘性）、`RequestRoundRobin`、`WeightedRoundRobin` 三种轮转策略 selector。agent 场景下"同一对话换 provider 丢上下文"风险高，单 Failover 已覆盖核心需求。


#### B3. 事务性配置切换 + 实时文件快照回滚
- **位置**：`CodexPlusPlus/crates/codex-plus-core/src/relay_switch.rs`（`switch_relay_profile_in_home` L18、`LiveFilesSnapshot` L70）
- **描述**：切换供应商前先 `capture_app_state_snapshot_nonfatal` 留快照，`LiveFilesSnapshot::capture` 读 config.toml + auth.json 原始字节，保存 settings，然后 apply。apply 失败时：先回滚 settings.json，再 `live_snapshot.restore` 把 config.toml/auth.json 字节级还原，两步都报错就拼成一条带两个子错误的消息。还有 `backfill_profile_before_switch`——切换前先把当前实时配置回填到旧 profile，避免覆盖用户在官方端做的手改。

#### B4. 多数据库会话发现 + 撤销（带白名单 + SAVEPOINT 预检）⭐
- **位置**：`CodexPlusPlus/crates/codex-plus-core/src/codex_sqlite.rs`（`codex_session_db_paths_from_home` L29、`codex_sqlite_dir_dbs_with_tables` L91）+ `crates/codex-plus-data/src/storage.rs`（`undo_backups`/`restore_backups`/`preflight_restore_rows`/`backup_source_db`）
- **描述**：会话可能散落在 `~/.codex/sqlite/*.db`（多个）+ legacy `state_5.sqlite`。发现策略：枚举 `sqlite/` 目录下所有 `.db/.sqlite/.sqlite3`，用 `SQLITE_OPEN_READ_ONLY` 打开查 `sqlite_master` 判断是否含目标表，按"codex-dev.db 优先"排序。删除时遍历所有候选 db 都删，撤销 token 设计成可序列化 JSON 数组（多 db 时是 `[token1, token2]`，单 db 时兼容裸 token）。关键修复：撤销时用 `backup_source_db` 校验"备份来自的 db 必须在 `allowed_db_paths` 白名单内"（防路径穿越），并且引入 `preflight_restore_rows`——用 SQLite `SAVEPOINT` 做一次试还原再 ROLLBACK，预检冲突，真正还原在第二个事务里做。
- **借鉴价值**：cursor-switch 如果也要读写 Cursor 的本地 SQLite 会话库，这套"按表探测发现多 db + 白名单校验源 db 路径 + SAVEPOINT 预检 + 多 token 数组兼容"是教科书级的安全持久层设计。尤其 `allowed_db_paths` 白名单防止"备份里塞一个恶意路径让恢复时写到任意文件"——这是真实安全洞。
- **移植难度**：中。需要 Go 的 SQLite 驱动（如 `modernc.org/sqlite` 纯 Go 无 cgo）。SAVEPOINT 预检模式可直接复用。

#### B6. 跨平台 Release 流水线（NSIS + DMG x64/arm64 + latest.json 自更新）
- **位置**：CodexPlusPlus `.github/workflows/release-assets.yml` + `scripts/installer/`
- **借鉴价值**：`latest.json` 自更新协议是 cursor-switch 做应用内更新可直接抄的轻量方案（不依赖 electron-updater）。cursor-switch 当前用 `update.json` + ed25519 强制签名（更安全），可对齐 latest.json 多平台结构。macOS bundle 结构校验 + 双架构矩阵也是 Wails 应用的标准操作。
- **移植难度**：低。

#### B7. 多用户/多实例端口隔离
- **位置**：`CodexPlusPlus/crates/codex-plus-core/src/ports.rs`（`guard_port_offset` L18）
- **描述**：单实例守护端口原本硬编码，多用户 RDP 环境会撞。改成：环境变量精确端口 > 环境变量 offset > Windows 上 `USERNAME` 字节求和 mod 1000 作为 per-user offset > 其他平台 0。
- **借鉴价值**：cursor-switch 做 Cursor 桌面代理时，如果也要起本地 HTTP/WebSocket 服务，多用户/多实例端口冲突是真实问题（尤其 Windows）。
- **移植难度**：低。

#### B8. 诊断日志贯穿所有副作用操作
- **位置**：`CodexPlusPlus/crates/codex-plus-core/src/diagnostic_log.rs`；调用遍布 `protocol_proxy.rs`
- **描述**：每个副作用操作（上游请求、故障转移、CDP 注入、配置切换、localStorage 清理）都调 `append_diagnostic_log(event_name, json!({...}))` 写结构化诊断日志，失败时用 `_ = ...` 忽略错误不阻断主流程。
- **借鉴价值**：cursor-switch 做 byok 路由时，"每个供应商请求 + 失败 failover + 协议转换异常"都打结构化诊断日志，对排查"路由损失到底是损失在哪一步"是刚需。CodexPlusPlus 的"四事件 + willFailover 字段"日志模式可直接抄。
- **移植难度**：低。

#### B9. per-model 上下文窗口 + auto-compact 阈值 catalog 注入
- **位置**：`CodexPlusPlus/crates/codex-plus-core/src/model_catalog.rs` + `relay_config.rs`（`apply_context_limits_to_config`）
- **描述**：利用 Codex 原生的 `model_catalog_json` 机制——生成一个 catalog JSON 文件，config.toml 里放指针，Codex 运行时按当前模型名查对应上下文窗口。每模型可配窗口 + 独立 auto-compact 阈值。
- **借鉴价值**：这是 Codex 专属机制，但思路"用宿主原生 catalog 机制注入 per-model 配置，而不是自己维护一套"值得 cursor-switch 参考——如果 Cursor 有等价的模型 catalog 配置点，优先走原生机制比自己外挂更稳。
- **移植难度**：高（Cursor 是否有等价机制未知，需先调研）。

#### B10. 文档约定（AGENTS.md / HANDOVER.md / THIRD_PARTY_NOTICES.md）
- **位置**：CodexPlusPlus 根目录
- **借鉴价值**：AGENTS.md（给 AI agent 的仓库工作规范）和 HANDOVER.md（跨 session 工作交接）这两个约定对任何长期维护的开源项目都值得引入。THIRD_PARTY_NOTICES.md 对注入第三方脚本/资源的项目是合规必要。
- **移植难度**：低（纯文档约定）。

### C. CodexPlusPlus 明确不做的（边界说明）

- **不做 agent loop / tool use / context compression engine**——这些全部委托给 Codex 桌面客户端。它只管"请求怎么路由到上游、协议怎么转、响应怎么转回来"。所以如果 cursor-switch 的 agent 核心要借鉴，CodexPlusPlus 能给的是**传输/路由/配置层**的工程实践，**agent loop 本身没有可借鉴的代码**。
- **不做定价计算**——`codex-models.json` 只含模型元数据（reasoning levels/shell_type/priority），无价格表；token 计量也只是透传上游 usage 字段（`chat_usage_to_responses_usage` 处理多种字段名兼容），不自己计费。所以"成本统计"这块对 cursor-switch 没有可直接借鉴的现成实现——这一块 cursor-switch 反而比 CodexPlusPlus 强。

### 5.8 已确认的正面边界

- Router 在已经向客户端发送事件后不会切换备用 provider，不会拼接两家输出（B2 `sinkStarted` 闸门）。
- Provider response body 均有关闭；非 2xx 错误摘要有大小限制。
- Updater 的最终 manifest 签名和资产 SHA-256 校验边界总体正确。
- 更新安装路径作为独立 argv 传递，未发现 shell 命令注入。
- MITM 和 backend 默认监听字面 loopback，不是 LAN 开放代理。
- 默认转发会清理 hop-by-hop 和若干敏感头。
- 未发现 `InsecureSkipVerify`、明显 SQL 注入或新的字符串命令拼接链。
- 未发现桌面 UI 使用 `innerHTML`、远程脚本或明显 HTML 注入链。
